# hubdouble plan

hubdouble is a local stand-in for GitHub: one small Rust binary that serves the GitHub REST API, the GraphQL API, App webhooks, OAuth sign-in and the Actions OIDC issuer closely enough that a GitHub App can run end to end against it. The first client is `octo-org/client`, called the client below. Everything the client calls must work. Everything else in GitHub's published API is routed and answers `501` until a later change implements it.

This plan is written for a swarm of agents. Phase 0 builds the frame and freezes the contracts in section 6. Phase 1 runs about a dozen agents in parallel, one per track, each in its own worktree and branch, each owning a disjoint set of crates and files.

hubdouble is written in Rust. Rounds 1 to 12 of the council review approved the behaviour (sections 1, 2 and 4) on a Go draft; from round 13 the plan is the Rust one, and sections 3, 5, 6, 7, 8, 9, 10 and 11 were rewritten for it. The client is still a Go program that calls GitHub through go-github v93, so the client behaviour the plan cites (escaping, headers, how a call reads an answer) is go-github's.

## 1. Goals

- **G1 Coverage of the client.** Every REST route in [docs/inventory/rest-routes.txt](inventory/rest-routes.txt), every GraphQL document in [docs/inventory/graphql/](inventory/graphql/), every webhook event in section 4.3, every response variant in section 4.8, the OAuth web, device and SSO flows, App JWT and installation tokens, and the Actions OIDC issuer work as GitHub does. A conformance suite (section 8) proves it, and CI fails when an inventory item does not pass.
- **G2 Fidelity.** Status codes, error bodies, headers, pagination, JSON shapes (including explicit `null`s), node IDs, permission checks and webhook payloads match GitHub. Responses are validated in tests against GitHub's OpenAPI description, GraphQL documents against GitHub's schema with GitHub's observed validation rules (section 4.7), and webhook payloads against `@octokit/webhooks` schemas.
- **G3 Room to grow to all of GitHub.** The full OpenAPI operation table and the full GraphQL schema are built in from day one. Adding an operation is one handler and one registration line, and `hubdouble coverage` reports the share implemented.
- **G4 Light and fast.** One static binary, no git binary, no database, pure Rust apart from the allocator (section 3). Targets in section 9.
- **G5 Scriptable.** A seed file and an admin API create every object a test needs without a UI. Tests wait on events (a drained delivery queue), never on time.
- **G6 Runs in Kubernetes as-is.** Plain HTTP on port 8000 behind a Service, configured by environment variables.

### 1.2 Prerequisite outside this plan

The client hard-codes `https://api.github.com` (`internal/ghapp/ghapp.go:44`), `https://github.com` (`internal/dispatch/accounts.go:48`) and the Actions issuer (`internal/oidc/oidc.go:36`, checked at `:105`). The client's local end-to-end work (branch `feat-funny-local-agent-e2e`) adds `CLIENT_GITHUB_DOUBLE` (`http://hubdouble:8000` in the local cluster) and the Actions issuer override, refused outside `CLIENT_ENVIRONMENT=Local`. That change is owned by the client's session, not by this plan. hubdouble's own conformance suite does not depend on it: it drives hubdouble with the requests go-github v93 makes, pointed at the test server (section 8). Only the phase 2 Kubernetes smoke test with the real client service waits for it. The same change decides whether the client's checks that a link starts with `https://github.com/` follow the double; the client's session decided to keep those checks, so the example sets `HUBDOUBLE_WEB_URL=https://github.com`. The same client change adds `mise run e2e:up` and the local smoke that phase 2's real-service step runs; that step waits for this change to merge. Section 4.10 is the contract those tasks are written against.

## 2. Non-goals for v1

- A web UI. The only pages are the OAuth authorize, SSO and device pages, and each can be skipped with query parameters.
- Git over HTTP or SSH (clone, fetch, push). The client does not use it. The object store in section 6.4 can serve it later (section 11).
- Line-level (diff3) content merges. The client merges branches through `POST /repos/{o}/{r}/merges` (`Repositories.Merge`, `internal/gitwrite/tree.go:327`); PRs become merged as section 6.4 says.
- Persistence across restarts. State lives in memory; reset goes back to the seed.
- REST search. The client searches only through GraphQL.
- GitHub Enterprise admin APIs, billing, Copilot, Packages, Pages, Codespaces, Projects v2, Discussions.
- Running Actions workflows. hubdouble records dispatches and lets a test or a fake runner drive a run's lifecycle.
- Multi-node operation.
- Rate limit enforcement beyond static headers and fault injection (section 4.7).

## 3. Decisions

Every crate is pinned to its latest stable version when P0-A adds it, and kept current.

| Area | Decision | Why |
| --- | --- | --- |
| Language | Rust, latest stable at start (pinned in `rust-toolchain.toml`), edition 2024, one Cargo workspace (section 5) | static binary, small memory, no garbage collector pauses, data races ruled out by the compiler |
| Runtime and HTTP | `tokio` (multi-thread runtime, worker count from `HUBDOUBLE_WORKERS`, default the CPU count) and `hyper` 1 with `hyper-util` (HTTP/1.1 and h2c), no web framework; a router generated from the OpenAPI operation table (section 6.2) | a framework router cannot hold GitHub's table: `GET .../issues/comments/{comment_id}` and `GET .../issues/{issue_number}/events` both match `.../issues/comments/events`, and GitHub has parameters that hold slashes (`git/ref/{ref}`, `contents/{path}`, `branches/{branch}`, `compare/{basehead}`) |

| State | in memory, one `parking_lot::RwLock`, typed tables with indexes, entities held as `Arc` and replaced on write, an undo log for rollback | fastest and simplest for one local process; readers keep a snapshot without a copy |

## 4. Behaviour

### 4.1 Process and URLs

One listener, `HUBDOUBLE_ADDR` (default `:8000`). `HUBDOUBLE_BASE_URL` (default `http://localhost:8000`) is the origin written into every URL in a response or payload, except the resource links below. `HUBDOUBLE_WEB_URL` (default the base URL) is the origin of `html_url` and other links to resources only. Pages hubdouble serves itself always use `HUBDOUBLE_BASE_URL`: `/login/oauth/*`, `/login/device` and the device flow's `verification_uri`, `/orgs/{org}/sso` and the `url=` in `X-GitHub-SSO`, so a person signing in locally never lands on real GitHub (the client shows `verification_uri` to people, `internal/dispatch/accounts.go:91-109`). Set `HUBDOUBLE_WEB_URL` to `https://github.com` when a client checks that links are GitHub's, as the client's draft notice does (`internal/report/surfaces.go:152`). API URLs in answers and payloads (`url`, `issue_url`, `pull_request.url`, `repository.url` and the like) always use `HUBDOUBLE_BASE_URL` with the API prefix the request came in on, because clients compare them with their API base (the client's `internal/dispatch/request_original.go:199`). `HUBDOUBLE_OIDC_ISSUER` overrides the issuer, which is `HUBDOUBLE_BASE_URL + "/_actions"` by default. An override may change the origin only: its path must end in `/_actions`, where hubdouble serves discovery and JWKS, and any other path fails at start.

| Path | Serves |
| --- | --- |
| `/` and `/api/v3/` | REST API |
| `/graphql`, `/api/graphql` and `/api/v3/graphql` | GraphQL (go-github resolves `NewRequest("graphql")` against its base URL, so a base of `/api/v3/` sends it to `/api/v3/graphql`) |
| `/login/oauth/authorize`, `/login/oauth/access_token`, `/login/device/code`, `/login/device`, `/orgs/{org}/sso` | OAuth and SSO |
| `/_actions/.well-known/openid-configuration`, `/_actions/.well-known/jwks`, `/_actions/token` | Actions OIDC issuer |
| `/_blobs/{id}` | redirect targets for job logs and release assets, with `HEAD` and `Range` |
| `/healthz`, `/readyz` | liveness and readiness (GitHub has no route there) |
| `/_hubdouble/` | admin API, metrics |

### 4.2 Authentication and authorization

| Kind | How it is made | Rules |
| --- | --- | --- |
| App JWT | client signs RS256 with the App's private key | `iss` is the App ID or client ID; refused when `exp` is past, when `exp` is more than 10 minutes after the server's now, or when `iat` is more than 60 s after now ([GitHub](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app)) |
| Installation token `ghs_` | `POST /app/installations/{id}/access_tokens` | 1 h expiry; `repositories`, `repository_ids` and `permissions` narrow it and are returned; asking beyond the installation's grant is `422`; `DELETE /installation/token` revokes it |
| User token `ghu_`, refresh `ghr_` | OAuth web or device flow | 8 h expiry, refresh 6 months, refresh rotates both |
| Personal token `ghp_` | seed or admin API | a script acting as a user |
| Admin token | `HUBDOUBLE_ADMIN_TOKEN` (default `hubdouble-admin`) | admin API only |

One choke point decides every REST request: the middleware resolves the actor, then checks the operation's `Requirement` (section 6.2) against the actor's grant and the target repository. A repository the actor cannot see is `404`. A missing permission is `403` with `X-Accepted-GitHub-Permissions`. A classic token (a personal `ghp_` token, or an OAuth App `gho_` token seeded with its scopes) needs one of the operation's `Requirement.scopes`, which are the scopes live GitHub names in `X-Accepted-OAuth-Scopes` for that operation; a token without one is `403` with that header. A read whose docs ask a scope only "with a private repository" lists no scope, because a private repository is already `404` to a token without `repo`, so a token without scopes reads public reviews and runs as an anonymous caller may ("No scope: Grants read-only access to public information", [scopes docs](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps#available-scopes)). A write to a repository needs `repo`, or `public_repo` for a public one. An implemented operation without a `Requirement` fails a test that walks the registry, so access is denied by default.

GraphQL has the same check at one place too: every resolver reaches a repository, org or node only through `gql::Ctx::load` (P0-B, backed by P0-D), which applies the actor's grant per object. A hidden repository in one alias answers `null` with `NOT_FOUND` for that alias while the other aliases answer; `node` and `nodes` answer `null` for hidden objects; search drops them. A mutation checks write access on its target before any change inside its `Update`, so a denied mutation changes nothing. A phase 0 test with test-only resolvers covers a visible and a hidden alias in one document and a denied mutation that leaves a ref as it was; T4 and T10 repeat it with the real `updateRefs` and `repository`.

### 4.3 Webhooks

Each App has one webhook (URL, secret, active flag), set in the seed, at App creation or later through the admin API. Every event on an account or repository where the App is installed, and that the App subscribes to, is delivered; `installation`, `installation_repositories`, `installation_target` and `github_app_authorization` are delivered whatever the subscription list holds, as on GitHub (the client reads their repository lists, `internal/webhook/resweep_asks.go:39`). Each delivery has `X-GitHub-Event`, `X-GitHub-Delivery` (a lowercase UUID, as GitHub sends; the client's `internal/store/store.go:27` accepts only `[0-9A-Za-z-]`, at most 64 bytes), `X-GitHub-Hook-ID`, `X-GitHub-Hook-Installation-Target-Type`, `X-GitHub-Hook-Installation-Target-ID`, `X-Hub-Signature-256`, `X-Hub-Signature`, `Content-Type: application/json` and `User-Agent: GitHub-Hookshot/hubdouble`. Payloads carry `installation`, `repository`, `organization` and `sender` as GitHub does, and every field GitHub's payload has; the octokit schemas check the shape, and the conformance case per event asserts the fields the client reads (its `internal/webhook/payload.go`), among them `push` `ref`, `before`, `after`, `created`, `deleted`, `forced` and `commits[].added|removed|modified`; `pull_request_review_thread` `thread.comments[].pull_request_review_id`; `check_run.requested_action` `requested_action.identifier` with `check_run.external_id`, `name` and `head_sha`; `release.tag_name`; `workflow_run` `path`, `head_sha`, `head_branch`, `event`, `run_attempt`, `html_url`, `name`, `conclusion` and `pull_requests[].number`. A `ping` goes out when an App's webhook is set.

Deliveries go through a bounded queue (capacity 10 000) and a small worker pool, in commit order. `Update` appends its events to an outbox with a commit sequence number while it holds the lock (an append, never a wait); one publisher task moves the outbox to the worker queue strictly in sequence order, so two concurrent writers cannot reorder each other. The outbox and the worker queue together hold at most 10 000 events and 32 MiB of payload (`Options::queue_capacity` and `Options::queue_bytes`), and the store checks both at commit under the lock, so neither a writer nor the publisher waits for space. A payload is held as its serialized JSON body, made once in `emit`. An event past either bound is not dropped: it gets its delivery ID in order and is logged at once as a failed delivery with `status_code: 0`, the status `Queue full` and no attempt, so a redelivery can send it later. The one exception: while such records wait in the outbox, an App keeps at most `log_capacity` of them, and the oldest past that is removed before it gets a delivery ID, because that many newer records of the same App would push it out of the App's delivery log ring before anyone could read it. Reason: with parsed payloads and no bound, a run of 16 writers against a receiver that answers in 2 s grew RSS by 356 to 993 MiB over 24 000 events; 32 MiB (about 3 400 `issue_comment` payloads) plus the idle RSS (under 40 MB) stays well inside the 128 Mi memory limit of the k8s deployment. The request and response (headers and bodies) of the deliveries of every App share one more budget of 8 MiB (`Options::log_bytes`, the `LOG_BYTES` default), counted from the start of an attempt, through the wait behind a slower lower ID, to the delivery log, `Queue full` records included; past it the oldest deliveries lose their request and response and keep every other field, so the list and the client's walk see them unchanged, while `GET /app/hook/deliveries/{id}` and a redelivery of such a delivery answer `404`, as for a delivery past GitHub's 3-day retention (`docs/fidelity.md`). Measured with `mise run bench`, each case in its own process: the slow case grows RSS by about 70 MiB, and a delivery log filled with 50 000 deliveries of 10 KB payloads by about 64 MiB, so idle RSS plus either stays inside 128 Mi; the bench gates each growth at 128 Mi minus the 40 MB idle target. A test runs two concurrent writers and checks delivery order. Delivery IDs are assigned at enqueue, so two attempts that finish in reverse order still list by ID, and a test reads both through the client's walk (`internal/reconcile/reconcile.go:673`). Each attempt has GitHub's 10 s timeout. Each attempt is logged with an `int64` `id` (go-github v93 `HookDelivery.ID`; the client walks down until `id <= floor`, `internal/reconcile/reconcile.go:674`) and the UUID as `guid`, plus `delivered_at`, `redelivery`, `duration`, `status`, `status_code`, `event`, `action`, `installation_id` and `repository_id`, for `GET /app/hook/deliveries` (newest first, cursor pagination with `cursor` in the `Link` header, `status=failure` filter, `per_page`), `GET /app/hook/deliveries/{id}` (request and response) and `POST /app/hook/deliveries/{id}/attempts`. A delivery older than 3 days by the injected clock leaves the list, and its read and redelivery answer `404`, as GitHub keeps deliveries for 3 days. The list shows an attempt only after every attempt with a lower ID for that App has finished, so a scan between two out-of-order completions never sees a later ID first and saves it as its cursor (the client's `internal/reconcile/reconcile.go:740-762`); a test scans between the two completions. A redelivery keeps the original GUID, gets a new delivery ID and has `redelivery: true`. There is no automatic retry. `POST /_hubdouble/hooks/drain` returns once every event committed before the call has left the outbox and the publisher, the worker queue is empty, no attempt is in flight and every attempt is logged. Deliveries carry the state epoch they were committed in. Reset, under the store lock, clears the outbox and the worker queue and moves to a new epoch, then releases the lock and returns only after attempts already in flight have finished (it never waits while it holds the lock, since a finishing attempt writes its log entry); an attempt from an older epoch adds no delivery log entry, and no attempt from an older epoch starts after reset returns. A test resets while attempts are queued and in flight and checks that no request reaches the receiver and no log entry appears after reset returns.

### 4.4 OAuth and SSO

- Web flow: `/login/oauth/authorize` with `client_id`, `redirect_uri`, `state`, `code_challenge` and `code_challenge_method=S256` answers `302` to the supplied `redirect_uri`, on whatever origin it names, with `code` and the unchanged `state` added to its query (the client sends its own callback and refuses one without the original `state`, `internal/dispatch/accounts.go:62`, `internal/staff/auth.go:223`). The signed-in user is the `login` query parameter, else the `hubdouble_login` cookie, else the seed's default user.
- `/orgs/{org}/sso?return_to=...` records SSO for the user and that org and redirects to `return_to` (same origin only). An org can be seeded as SSO-enforced: a user token without SSO for it gets `403` with `X-GitHub-SSO: required; url=...` on that org's resources, `GET /orgs/{org}/repos` included (the client probes there, `internal/dispatch/accounts.go:229`).
- `/login/oauth/access_token` checks per grant what GitHub checks: the code grant needs `client_id`, `client_secret`, `code`, the `redirect_uri` the code was made for and the PKCE verifier; the device grant needs only `client_id`, `device_code` and `grant_type` (what the client sends, `internal/dispatch/accounts.go:118`); the refresh grant needs `client_id`, `client_secret` and `refresh_token`. It answers form-encoded by default and JSON with `Accept: application/json`. Errors answer `200` with an `error` field (`bad_verification_code`, `incorrect_client_credentials`, `redirect_uri_mismatch`, `bad_refresh_token`, `unsupported_grant_type`, and `unverified_user_email` for a seeded user marked unverified), as GitHub does.
- Device flow: `/login/device/code` returns `device_code`, `user_code`, `verification_uri`, `expires_in` and `interval`, or `device_flow_disabled` when the App has it off. Polling (`grant_type=urn:ietf:params:oauth:grant-type:device_code`) answers `authorization_pending`, `slow_down` with a new `interval` 5 s longer, `expired_token`, `access_denied`, `incorrect_device_code`. A test approves with `POST /_hubdouble/oauth/device/{user_code}` (`login`, `approve`).
- Refresh: `grant_type=refresh_token` rotates both tokens.
- A conformance case sets `HUBDOUBLE_WEB_URL` to another origin and asserts that `verification_uri`, the authorize page and the SSO header still use the base origin, and that the authorize answer redirects to a `redirect_uri` on a third origin with `code` and the same `state`.

### 4.5 Actions

- Workflows are the files under `.github/workflows/` on the default branch, with stable IDs per path.
- The `{workflow_id}` path segment takes the numeric ID or the file name (`agent.yml`), for dispatches, runs and the workflow itself; the client uses the file name (`CreateWorkflowDispatchEventByFileName`, `ListWorkflowRunsByFileName`).
- `POST .../dispatches` checks the ref and inputs against the workflow's `workflow_dispatch` block (an undeclared input, a missing required input (`Required input 'name' not provided`), an unknown ref, a `choice` or `boolean` value outside its allowed values (`Provided value 'v' for input 'name' not in the list of allowed values`) or an array or object value (`Invalid value for input 'name'`) is `422`, as on GitHub, with only GitHub's `message` and the operation's `documentation_url`, and no `errors` (octocrab issue 406); a declared input that is not sent takes its `default`; for undeclared inputs the message is GitHub's `Unexpected inputs provided: ["a", "b"]`, naming every undeclared input in double quotes, sorted by name, and with no other text that could hold an input name (the client matches each name as a substring of the whole message, `internal/dispatch/dispatch.go:759`); a workflow without a `workflow_dispatch` trigger answers `422` with GitHub's `Workflow does not have 'workflow_dispatch' trigger`, which the client matches, `internal/dispatch/dispatch.go:739`; because the client retries without inputs only when that message names all it sent, `internal/dispatch/dispatch.go:717`; a `422` creates no run and emits nothing), and otherwise creates exactly one run (`queued`) with one job per job key, emits `workflow_dispatch`, `workflow_run.requested` and `workflow_job.queued`, and answers `204`, or `200` with `workflow_run_id`, `run_url` and `html_url` when the body has `return_run_details: true`.
- `POST /_hubdouble/actions/runs/{id}` moves a run (`status`, `conclusion`, per-job steps, logs and check run annotations) and emits the matching events. A seed policy `actions.auto_complete: success|failure|none` completes runs at once.
- Runs, attempts, jobs, cancel, rerun, rerun-failed-jobs and a job's rerun (each a new attempt; a job's rerun and rerun-failed-jobs also queue the jobs that need the chosen ones, and carry the rest as new jobs that keep their state), repo and org secrets (metadata only) and variables follow GitHub's shapes. Job logs answer `302` to `/_blobs/{id}`.
- Every workflow run has a check suite of the GitHub Actions App (ID 15368, slug `github-actions`, owner `github`, which T2 serves through `/users/github` and `/user/9919` with the live profile unless a seeded account holds that login or ID), and every job is a check run in it with the job's ID and node ID (`CR_`), as on GitHub. T8's `hubdouble_api_checks::actions` owns those rows; T9 writes them only through it, in the same transaction and from the same function that writes the job, so a job and its check run never differ. The suite takes the status and conclusion of the run's latest attempt, and keeps its ID across attempts. Every check suite on a commit, of any App and event, takes `before` and `after` from the first push that made the commit the tip of a branch or tag (an annotated tag counts for the commit it peels to, and refs outside `refs/heads/` and `refs/tags/` do not count), with zeros as `before` for a created ref, and keeps them when the ref moves on, as the live suites on goreleaser/goreleaser `a6edafa` and cli/cli `233b470` and `42d52b4` show. A re-run adds the new attempt's jobs as new check runs in the same suite, so `filter=latest` counts the newest check run per name and `filter=all` every attempt. No local App holds ID 15368 or the slug `github-actions`: the seed and the admin API refuse both with `422`, ID allocation skips 15368, and the Checks API takes no write from an installation with that App ID. The Checks API refuses a write to such a check run from any other App with GitHub's `403` (`Invalid app_id` ... `can only be modified by the GitHub App that created it.`). Subscribed Apps get `check_run.created`, `check_run.completed` and `check_suite.completed` for them; the `requested`, `rerequested` and `requested_action` actions go to the owning App only, so no App gets them.
- A re-run of a run created more than 30 days before (counted from its first attempt, with the injected clock) answers `403` with `Unable to retry this workflow run because it was created over a month ago` and `documentation_url` `https://docs.github.com/rest/actions/workflow-runs#re-run-a-workflow`, as GitHub does ([cli/cli#9989](https://github.com/cli/cli/issues/9989)). A re-run past the 50th answers `201` and gives an attempt that completes at once with `failure` and no jobs, so the suite fails ([GitHub changelog](https://github.blog/changelog/2026-04-10-actions-workflows-are-limited-to-50-reruns/); the rest is in `docs/fidelity.md`).
- OIDC: discovery and JWKS under the issuer. `POST /_hubdouble/actions/oidc/token` mints a token for a run with `iss`, `sub`, `aud`, `exp`, `nbf`, `iat`, `jti`, `repository`, `repository_id`, `repository_owner`, `repository_owner_id`, `repository_visibility`, `ref`, `ref_type`, `sha`, `workflow`, `workflow_ref`, `workflow_sha`, `job_workflow_ref`, `job_workflow_sha`, `run_id`, `run_number`, `run_attempt`, `check_run_id`, `actor`, `actor_id`, `event_name`, `environment`, `runner_environment`, each overridable in the request. `exp`, `nbf` and `iat` are JSON numbers; every other claim, IDs, `run_number` and `run_attempt` included, is a string, as in [GitHub's example token](https://docs.github.com/en/actions/concepts/security/openid-connect#understanding-the-oidc-token). `job_workflow_ref` and `job_workflow_sha` default to the reusable workflow the seed names for the repository's caller (for v5, `octo-org/runner/.github/workflows/agent.yml@<the 40-hex commit the caller pins>`, which a release tag peels to), so the client's v5 release check (`internal/oidc/oidc.go:250`) accepts the token; hubdouble's conformance checks those claims, and the real-service proof waits for the runner step the client's session adds later. Tokens are RS256 with a `kid` from the JWKS. Discovery is at `<issuer>/.well-known/openid-configuration` and its `jwks_uri` is on the same origin (the client's `internal/jwks/jwks.go:303` requires that). Each run also has a request token, and `GET /_actions/token?audience=...` with it answers like `ACTIONS_ID_TOKEN_REQUEST_URL`, so `@actions/core.getIDToken` works unchanged in a fake runner.

### 4.6 Seed and admin API

The seed (`HUBDOUBLE_SEED`, YAML or JSON) is a list of the objects the admin API takes, applied at start in the kind registration order: P0-F's kinds first (users, orgs, repositories, Apps, installations, tokens), then each track's kinds in the `register_all` order of section 5 (teams after repositories, so a team can name its repositories), and in file order within a kind, except that a `fork_of` parent is applied before its fork. The list below groups the objects, it is not the order:

- users (ID, login, name, email, type User or Bot, personal tokens given or generated, each with classic OAuth `scopes`, default `repo`, `workflow`, `read:org` and `user`, so a seeded token reaches the user's private repositories as a real one would)
- orgs (ID, members and roles, SSO enforced), teams (ID, parent, privacy, members and roles, repositories and permission)
- repositories (ID, owner, name, visibility, `fork_of`, default branch, files as a path to content map or `from_dir`, extra branches, annotated and lightweight tags, collaborators, rulesets, releases with assets)
- Apps (ID, slug, name, owner, client ID and secret, a public key alone or a private key given or generated, webhook URL and secret, permissions, events, device flow on or off)
- installations (ID, App, account, repository selection and list, permissions, suspended)
- Actions policy, OIDC signing key (given or generated), default OAuth user

A repository's history is an ordered `commits` list: each entry names a branch, the file changes, a message, and optional tags (annotated or lightweight) on the commit it makes, and each entry's parent is the branch's previous commit, so a branch can hold commits on top of a tagged commit. File contents may hold `{{sha "<owner>/<repo>" "<ref>"}}`, which the loader replaces with the commit that ref resolves to (a tag peels to its commit); the ref must come from an entry applied earlier, else the seed fails to load with the entry's position. This is how `releases.json` and the caller's pin name a tag's commit without a hand-computed SHA. Any string value in the seed may hold `{{env "NAME"}}`, which the loader replaces with that process environment variable; an unset or empty variable fails the load with its name and the entry's position. Per-cluster values (keys, webhook URL and secret, tokens) come in this way, so a seed file holds no secret.

Seeded commits and tags are deterministic: author, committer and tagger default to a fixed seed identity and the fixed time `2026-01-01T00:00:00Z` unless the seed gives them, and files are written in sorted path order, so the same seed file gives the same SHAs on every start and every reset. A seed test loads the example seed on two fresh servers and checks that each tag peels to the same commit and that the target caller's pinned SHA is that commit.

`GET /_hubdouble/log` (a ring buffer of the last 50 000 entries; a cursor older than the window answers `410`) lists every API request (method, path, operation ID, actor, status) and every emitted event and delivery since a cursor, and `GET /_hubdouble/log/wait?match=...&after=<cursor>` holds the request open until a matching entry exists (or the caller's own timeout ends it), so a smoke script waits on "installations listed", "reaction added" or "workflow run created" without sleeping. Applying the seed at start and on reset is silent: it emits no events and no deliveries. Creates and changes through the admin API emit events as section 4.3 says. Reset restores the table snapshot taken right after the seed load, so every seeded object, with a given ID or not, comes back with the same ID and number (the seeded PR stays `1`), but every generated sequence (object IDs, delivery IDs, run IDs, issue and PR numbers, log cursors) keeps counting up from where it was, because a running client keeps IDs and cursors across a reset (its delivery walk stops at the first ID at or below its stored floor, `internal/reconcile/reconcile.go:711-746`, and it binds run IDs to dispatches, `internal/dispatch/dispatch.go:648`). Reset empties the request log, and a `/_hubdouble/log` cursor from before the reset answers `410`, including a `/_hubdouble/log/wait` request held open across the reset. Reset keeps the App delivery log (a ring buffer of the last 50 000 attempts per App), as GitHub keeps deliveries, so a running client resumes its saved page cursor and its walk still reaches an ID at or below its stored floor without recording a source gap (`internal/reconcile/reconcile.go:714`, `:754-761`). A `GET /app/hook/deliveries` `cursor` hubdouble never issued, or one that points past the ring buffer, answers `422`, because the client clears a saved delivery cursor only on `400` or `422` (`internal/reconcile/reconcile.go:725`, `:858-861`). hubdouble's own tests get repeatable IDs from a new server per test, not from reset. Reset keeps every unexpired issued token whose installation or user is in the seed, because the client's installation client hands the first `401` back to its caller before it mints again (`internal/ghapp/ghapp.go:126`). The admin API under `/_hubdouble/` (admin token) creates, reads, updates and deletes each of these, reads generated keys and tokens, resets the state to the seed (`POST /_hubdouble/reset`), drains webhooks, injects events and faults, approves device codes and drives Actions runs. Each track registers the admin routes and seed kinds for the objects it owns through the contract in section 6.6.

### 4.7 Fidelity rules every track follows

- Errors: `{"message", "documentation_url", "status"}`, plus `errors[]` with `resource`, `field`, `code` on `422`. One answer differs, as live GitHub does: a commit list `since` or `until` that Ruby's `DateTime.parse` cannot read answers `500` with `content-type: application/json; charset=utf-8` and an empty body (`gh api -i 'repos/cli/cli/commits?since=garbage'`, 2026-11-24). The test kit's docs check accepts an empty body only for the operation and status keys of its live-evidence table, which holds this one.
- An archived repository refuses every write at the one REST choke point with GitHub's `403` `Repository was archived so is read-only.` and the operation's documentation link (each generated operation carries its docs URL), and every GraphQL mutation at `MutCtx::authorize` with `UNPROCESSABLE` `Repository was archived so is read-only` (live samples: `brave/qa-resources` 625, `fedora-infra/webhook-to-fedora-messaging` 101, `sourcegraph/sourcegraph-public-snapshot` 26820). Reads and the writes GitHub still takes on an archived repository (`repos/update`, which unarchives, `repos/delete`, forks, stars and subscriptions) pass.
- A locked conversation takes a comment, a review comment, a review with a body or comments and GraphQL `addPullRequestReviewThread` only from a user with write access to the repository; anyone else, an installation token included, gets `403` `Unable to create comment because issue is locked.` with `documentation_url` `https://docs.github.com/articles/locking-conversations/` (live `jreleaser/jreleaser` 1871, `getsentry/sentry` 90249, an Actions token in `AlexTo/discava` 656; the [docs](https://docs.github.com/en/communities/moderating-comments-and-conversations/locking-conversations)). `PUT` and `DELETE .../issues/{n}/lock` set and clear it for writers and send `issues` or `pull_request` `locked` and `unlocked`.
- Commit statuses: `POST .../statuses/{sha}` refuses, with `422` `Validation Failed` and nothing written, a `description` longer than 140 characters and a `target_url` whose scheme is not `http` or `https`, with `errors` as one string (`Validation failed: Description is too long (maximum is 140 characters)`, `Validation failed: Target url must use http(s) scheme`; projectbluefin/lab issue 471 on 2026-07-28 and renovatebot/renovate issue 44119 on 2026-06-20 quote these live bodies; the client cuts its description to 140, `internal/approval/approval.go:18`), and a missing or unknown `state` or a `context` with a 4-byte character with an `errors[]` entry of resource `Status`, code `custom` and field `state` or `context`. A `context` is case-insensitive, as the docs say: the combined status, GraphQL `statusCheckRollup` and a required status check match contexts without case, and each status keeps the spelling it was created with.
- Pagination: `per_page` (default 30, max 100) and `page`, with a `Link` header; cursor pagination where GitHub uses it. A `Link` writes each query name once, at its first place, with its last value, escaped as GitHub escapes a query (a space is `+`), and sets `page` in its place. A page past the last links `prev` and `last` to the last page. Every page list answers `422` when `page * per_page` passes `i64::MAX`, and four lists stop sooner, as live GitHub does: the repository issue list without a cursor at `page * (per_page + 1)` over 10 000, the repository comment list at 30 000 results, releases at 10 000 and workflow runs at 40 000. The comment and run lists count at most that many results for the last page and `total_count`.
- An empty list renders as `[]`, never `null` (the client refuses a `null` matching-refs answer, `internal/dispatch/release_catalog.go:205`); the render layer marshals nil slices as empty arrays, and a test lists matching refs on a repository with no match.
- Conditional requests: every `200` `GET` has a weak `ETag` from the hash of the media type and the body, and a matching `If-None-Match` answers `304` (the client's `internal/dispatch/conditional.go` sends it, keyed by URL and `Accept`).
- Headers: `X-GitHub-Request-Id`, `X-GitHub-Media-Type`, `X-RateLimit-*` with realistic static values and `X-RateLimit-Remaining` never `0` unless a fault sets it (go-github skips calls while it is `0`), `X-OAuth-Scopes` for user tokens, `X-GitHub-Api-Version-Selected` on REST. `X-GitHub-Media-Type` names the first `application/vnd.github` range of `Accept` wherever it stands (`github.v3; param=sha` for `.v3.sha`, `format=json` only with a `+json` suffix), else `github.v3` when `Accept` holds `application/json`, `text/*` or `application/*` (any case), or `*/*` beside another range, else `github.v3; format=json` for no `Accept` or `*/*` alone. When the range of highest `q` (the first of equal ones) is none of those, the value starts with `unknown, `. An `Accept` with no such range (the release asset read also serves `application/octet-stream`, which every other route refuses) answers `415` with `message` `Unsupported 'Accept' header: '<ranges>'. Must accept 'application/json'.`, the ranges as sent and joined by `, ` in the order of their `q`, `documentation_url` `https://docs.github.com/v3/media` and `X-GitHub-Media-Type: unknown`, on REST and GraphQL. It comes after the credentials check and, for an anonymous caller, after the sign-in a write or a user, App or installation route needs, and before the repository lookup, so an absent repository also answers `415` (live GET reads of `repos/cli/cli`, `user` and absent repositories, and an authenticated GraphQL query, on 2026-11-24). REST `X-GitHub-Api-Version` accepts the versions GitHub publishes (`2022-11-28` and `2026-03-10` today; go-github v93 sends either); a request without the header is served as `2022-11-28`, and any other value is `400`. GraphQL reads no REST version: live `gh api graphql -i -H "X-GitHub-Api-Version: 1999-01-01" -f query='{ viewer { login } }'` answered `200` without `X-GitHub-Api-Version-Selected` (2026-11-24). Its media type follows the same rule with `v4` as the default version (`github.v4; format=json` for `*/*`, `github.v4` for `application/json`, `github.v3; format=json` for go-github's `application/vnd.github.v3+json`), its `X-RateLimit-Resource` is `graphql`, and a user token also gets `X-Accepted-OAuth-Scopes: repo`, as live answers on 2026-11-24 show. An anonymous `POST` or `GET` of `/graphql` answers `403` before its body or `Accept` is read, with GitHub's compact body `{"message":"API rate limit exceeded for <peer IP>. (But here's the good news: Authenticated requests get a higher rate limit. Check out the documentation for more details.)","documentation_url":"https://docs.github.com/rest/overview/resources-in-the-rest-api#rate-limiting"}` without `status`, `X-GitHub-Media-Type: github.v3; format=json`, `X-RateLimit-Limit`, `-Remaining` and `-Used` `0` and `X-RateLimit-Resource: graphql`, as live anonymous reads answered on 2026-11-24. An App JWT still answers `401`.
- Diff and patch media: `GET .../commits/{ref}`, `.../compare/{basehead}` and `.../pulls/{pull_number}` with `Accept: application/vnd.github.diff` (or `.v3.diff`) answer `git diff` text, and with `application/vnd.github.patch` one `git format-patch` mail per commit, as live GitHub writes them: path order, exact renames with `similarity index 100%`, git's default hunk function context, `Binary files ... differ` in a diff and `GIT binary patch` with full IDs in a patch, a 72-column diffstat with its summary, `[PATCH n/m]` for two or more commits, and no mail signature. A commit compares with its first parent, a compare and a pull request with the merge base. The client does not ask for these media.
- IDs: one global `int64` sequence. The seed loader reads every given ID before it applies any kind and starts the sequence above the largest; an admin create with a given ID that is taken or at or below the sequence answers `422`. Node IDs use GitHub's current format, a type prefix and an opaque payload (`PR_kw...`). Legacy base64 IDs are accepted, and the answer adds GitHub's `DEPRECATION` warning with `next_global_id` in `extensions`.
- Timestamps in RFC 3339 UTC with second precision.
- Reads of an unchanged ref answer the same commit every time.
- The delivery log is a ring buffer of the last 50 000 attempts per App.
- Commits GitHub writes itself (merges, `createCommitOnBranch`) have committer `GitHub <noreply@github.com>`, a signature from hubdouble's web-flow key, and `verification.verified: true`, reason `valid`. A commit an installation makes through the git data API with no `author`, `committer` or `signature` is signed the same way and reports `valid`, as GitHub signs a bot's API commit (the client's `internal/gitwrite/tree.go` `signedOn` refuses anything else). A client-signed commit from the git data API reports `unknown_key`; any other unsigned one `unsigned`.
- GraphQL validation follows GitHub's observed behaviour, which is the spec's rules with listed exceptions, each confirmed against real GitHub. The one known today: fields of the same name in different concrete types may differ in nullability (`PullRequest` on `IssueComment` and `PullRequest!` on `PullRequestReviewComment` in the client's `originalCommentEdit`; GitHub accepted that document on 2026-11-22).
- GraphQL execution follows the spec: a `null` from a failing non-null field propagates to the nearest nullable parent, and the error carries `type` (`NOT_FOUND`, `FORBIDDEN`, ...), `path` and `locations`. Connections require `first` or `last` (max 100) with GitHub's message. An unimplemented field is an error on its path only, `type: "HUBDOUBLE_NOT_IMPLEMENTED"`. A repository the actor cannot see answers `null` with a `NOT_FOUND` error for that alias only.
- Faults: `POST /_hubdouble/faults` with a method and path pattern (or GraphQL operation name), status, body, headers, delay and count, for a secondary rate limit, a `502` or `X-GitHub-SSO`.

Track crate names: `api-apps` (T1), `api-users` (T2), `api-orgs` (T3), `api-gitdata` (T4), `api-pulls` (T5), `api-reviews` (T6), `api-issues` (T7), `api-checks` (T8), `api-actions` (T9), `api-repos` (T10), `api-search` (T11). T12 owns `examples/`, `deploy/` and the release workflow, no crate.

A later track reaches an earlier track's rule only through a public item of that track's crate, never by copying it, as T9 writes check runs through T8's `hubdouble_api_checks::actions`. On GitHub a pull request is an issue, so `PATCH .../issues/{n}` with `state: open` reopens one as `PATCH .../pulls/{n}` and `reopenPullRequest` do; T7 calls T5's `hubdouble_api_pulls::reopen` and `reopened`, the one rule all three paths run, so they cannot disagree. `reopen` refuses, in this order, a merged pull request, a deleted base or head branch, another open pull request from the same head into the same base, and a head branch force-pushed or recreated since the close, each a `422` `custom` error on `state` with GitHub's message (`state cannot be changed. The pull request cannot be reopened.`, `... The {branch} branch has been deleted.` or `... The {base} and {head} branches have been deleted.`, `... There is already an open pull request from {head} to {base}.`, `... The {head} branch was force-pushed or recreated.`, as raw calls against GitHub recorded in sky-ai-eng/orrery#35 show), and `reopenPullRequest` answers `Could not open the pull request.` ([cli/cli#10062](https://github.com/cli/cli/issues/10062)). Otherwise it takes `head.sha`, `base.sha` and `mergeable` from the live branches. `reopened` sends `pull_request.reopened` through T5's renderer and no `issues` event, and records the `reopened` issue event in T5's `StateEvents` table, with the `closed` events of T5's own close; T7's `GET .../issues/{n}/events` lists those rows with its own, because T5 cannot depend on T7.

GitHub writes a pull request edit in parts, and a refusal keeps the parts written before it, as raw calls against GitHub recorded in sky-ai-eng/orrery#35 show. `PATCH .../pulls/{n}` ignores a `state` other than `open` and `closed` and writes the rest of the edit (orrery commit 1d86fa49, `state: parked` answered `200`), and a repeated body key takes its last value, as a repeated query key does and as the pulls list reads `state` (live `cli/cli` lists `state=closed&state=bogus` as open and `state=bogus&state=closed` as closed). It refuses a blank `title` before any write; then it writes the `body`; then, unless the reopen is refused, the `title` and the state change; last the `base`, judged against the state the pull request is left in. A refused `base` is a `422` `invalid` error on `base` (`Cannot change the base branch of a closed pull request.`, `Proposed base branch '{base}' was not found`, `There are no new commits between base branch '{base}' and head branch '{head}'`, `A pull request already exists for base branch '{base}' and head branch '{head}'`, checked in that order), and it is the answer even beside a refused reopen. `PATCH .../issues/{n}` keeps its `body`, labels and assignees beside a refused reopen and drops its `title`. A kept part sends its webhook and records its issue event, in GitHub's timeline order `renamed`, `closed` or `reopened`, `base_ref_changed`; T5 answers the refusal through `hubdouble_api_pulls::kept`, which returns GitHub's error body without the rollback of an `Err`, and T7 calls it too. T5's `StateEvents` holds T5's `renamed`, `closed`, `reopened`, `base_ref_changed`, `automatic_base_change_succeeded`, `automatic_base_change_failed`, `head_ref_deleted`, `head_ref_restored` and `base_ref_deleted` events, each with the REST keys of live GitHub (`grafana/grafana` pull requests 137169 and 137757, `llvm/llvm-project` pull request 244287).

A deleted branch changes the pull requests on it through T5's ref subscriber, so every deletion path (REST `DELETE .../git/refs/{ref}`, GraphQL `updateRefs`, and a merge) behaves the same. Each pull request whose head is the branch records `head_ref_deleted` and stays as it was, open ones with `mergeable` `null` (live `grafana/grafana` pull request 137757 and `nodejs/node` pull request 67519 stayed open after a deletion through the API); GitHub closes them only for a `git push` deletion (orrery#35), which hubdouble does not serve. Each open pull request whose base is the branch records `base_ref_deleted`, then closes with `closed` and the `pull_request` `closed` webhook, by the deleter (live `grafana/grafana` pull request 137169). A merge deletes the head branch as GitHub [documents](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-the-automatic-deletion-of-branches) only when the head repository has `delete_branch_on_merge`, the branch is not its default branch, no active ruleset with a `deletion` rule covers the branch ("Branch protection rules and repository rules can also prevent branches being automatically deleted"), no other open pull request has the branch as its head ("You cannot delete branches that are associated with open pull requests", [docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/creating-and-deleting-branches-within-your-repository#deleting-a-branch)), and the merger's grant allows `contents: write` on the head repository through `hubdouble_auth::authorize` (for a fork, "The user merging the pull request has write access to the fork"), so an installation that does not cover a fork leaves the fork's branch; before the deletion, each open pull request in the same repository whose base is that branch and whose head is in that repository moves to the merged pull request's base ([docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/creating-and-deleting-branches-within-your-repository#deleting-a-branch)) with `automatic_base_change_succeeded`, then `base_ref_changed` and the `edited` webhook after the deletion (live `llvm/llvm-project` pull request 244287); each other pull request on that base whose head is in that repository, such as a merged one, keeps its base and `updated_at` and records `automatic_base_change_failed` (prefix `ABCFE_`) by the merger before the deletion, with no webhook (live `getsentry/sentry` pull requests 132051 and 132005); an open pull request whose own head branch is gone, deleted through the API while it stayed open, cannot move, so it records `automatic_base_change_failed` and the deletion then closes it with `base_ref_deleted` and `closed`, and the merge stands; a pull request from a fork closes with the deletion (live `grafana/grafana` pull request 137169). A branch created again on any path, while it is the head of a pull request whose last head event is `head_ref_deleted`, records `head_ref_restored` (prefix `HRRE_`, the keys of `head_ref_deleted`) by the creator and moves `updated_at`, on an open or a closed pull request, with no `pull_request` webhook unless the head moved (live `grafana/grafana` pull request 138516 and `langchain-ai/langchain` pull request 41731).

T5's `hubdouble_api_pulls::mergeable_state` is the one `mergeable_state` rule; REST pulls, T6 and T7 renderers, webhooks and GraphQL `mergeStateStatus` call it. An open pull request answers, in this order: `unknown` while `mergeable` is `null`, `dirty` on a conflict, `behind` when an active `required_status_checks` rule on the base has `strict_required_status_checks_policy` and the head does not hold the base tip of the last test merge, `blocked` while a required check does not pass, a `pull_request` rule's approvals, its approval of the last push or its code owner review are missing or a required thread resolution is open, as the branch rules below decide, `unstable` while another latest check run or status does not pass (pending included), and `clean` otherwise. A check run passes when completed with `success`, `neutral` or `skipped`. A draft answers as a ready one: live GitHub never answered `draft` in about 60 sampled drafts (`jqlang/jq` 3750 `clean`, `astral-sh/uv` 23334 `clean` and 23370 `blocked`, `cli/cli` 14927 `blocked`), and the GraphQL schema marks `DRAFT` deprecated. The `behind` fact is stored with each test merge in T5's `MergeStates` table, and a close stores the state the pull request had, which it keeps (6.4). Live samples back each rule: `sharkdp/bat` 4148 `behind` with its strict required check passing and 4142 `blocked` with it failing, `jqlang/jq` 3726 `unstable` with a failing check and no rules, `astral-sh/uv` 23310 `clean` with an older failed attempt under a newer success.

T4's `hubdouble_api_gitdata::branch_rules` is the one rule set for every write that moves a branch: REST `.../git/refs`, GraphQL `updateRefs` and `createCommitOnBranch`, `POST .../merges` and `PUT .../pulls/{n}/merge`. Each write runs inside its transaction, checks the active branch rulesets after the git write and rolls back on a violation, so a git refusal such as a non-fast-forward keeps its own answer. A ruleset that the actor bypasses does not count: `always` and `exempt` skip it on every write and `pull_request` only on a pull request merge. The rules are `creation`, `update`, `deletion`, `non_fast_forward`, `pull_request` (a direct write needs a pull request, a pull request merge needs `merge` in `allowed_merge_methods`), `required_linear_history` and `required_signatures` over the commits that the write adds (for a new branch, those that no other branch holds, as GitHub documents), and `required_status_checks` (not on a new branch with `do_not_enforce_on_create`). A refusal is `Repository rule violations found` followed by each violation in rule order, each part ending in a blank line, with GitHub's texts: `409` for `POST .../merges` (Classmethod sample), `405` for a pull request merge, which adds the review violations (`At least N approving review(s) ...`, `N review(s) requesting changes ...`, `Waiting on 1 reapproval from someone other than the last pusher.`, an open conversation), `422` for `.../git/refs`, and `UNPROCESSABLE` in GraphQL. The same check, before any rule, refuses a deletion of the default branch with GitHub's `422` `Cannot delete the default branch` (live `lingrino/infra` 3039; `Y-O-W/dotfiles` issue 45 got this text with a deletion ruleset on the branch), and `UNPROCESSABLE` in GraphQL. It applies the active tag rulesets to `refs/tags/` writes (`creation`, `update` `Cannot update this protected ref.`, `deletion` `Cannot delete this tag`, `non_fast_forward` on the peeled commits `Cannot force-push to this tag`, `required_linear_history` and `required_signatures`), and, to every branch and tag write and to both merges, the active push rulesets of the repository and of the root of its fork network, which the root's bypass actors skip: `file_path_restriction` (`File path is restricted`), `max_file_path_length`, `file_extension_restriction` and `max_file_size` (in MB), over the files that each added commit writes against its first parent, without `ignored_file_paths`. The added commits are those the new tip reaches and the old tip and, for a new ref, no other branch or tag reaches, found by a walk that stops where they meet. With `strict_required_status_checks_policy`, a pull request merge whose head lacks the base tip finds every required check expected, as live GitHub refuses one with passing checks (`phuongnse/nexkit` issue 171). With `require_code_owner_review`, T5 reads the CODEOWNERS file of the base tip (`.github/`, the root, then `docs/`, with T4's `codeowners` parser that also serves `repos/codeowners-errors`), takes for each changed file the owners of its last matching line, and needs, for each distinct owner set with an owner who can write, an approval from one of them (a user, a member of a team with write access, or the account of an email); it blocks the merge with `Waiting on code owner review from A, B, and/or C.` before the other violations (live `bors-ng/bors-ng` 1521, `orq-ai/bartolo` 64), keeps `reviewDecision` at `REVIEW_REQUIRED` and `mergeable_state` at `blocked`. Both merges also refuse a merge that changes the `.github/workflows` tree of the base when the actor may not write workflows, with `403` and the operation's docs: an App or a user-to-server token without the `workflows` permission, or a classic or OAuth token without the `workflow` scope, each with GitHub's text for its kind (live `jordansmall/spindrift` 6450; update-branch answers `403` in `limitlessprojects/Go-Hybrid` 762). A required check reads, for each context, the test merge commit when it has a check run or status of that name and the head otherwise ("If the test merge commit has a status, the test merge commit must pass. Otherwise, the status of the head commit", [docs](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)); `POST .../merges` reads the merged head and a direct write the new tip. A check run and a commit status of one required name must both pass ("If a check and a commit status have the same name, both must pass when that name is required", same page). T5's merge state and `reviewDecision` read the same rules with no actor. The latest non-pending, non-comment review of each writer other than the author counts; `require_last_push_approval` needs an approval from someone other than the last pusher submitted after the last push that changed the diff, in the order that pushes land and reviews are submitted (a pending review started before the push and submitted after it counts), and a pull request with no recorded push takes its author as the pusher. With `dismiss_stale_reviews_on_push`, T6's ref subscriber compares the diff state (the merge base tree and the head tree) before and after each push to the head or base, and before and after each move of `refs/pull/{n}/merge`, whose old test merge commit gives the base and head before (this is how a base change through `PATCH .../pulls/{n}` or an automatic base change reaches it, when its computation ends). A change that keeps the head and only moves the merge base forward adds no change and keeps the approvals ("Merge bases changing under a pull request will preserve approvals in most situations where no new changes are introduced", [changelog](https://github.blog/changelog/2023-06-06-security-enhancements-to-required-approvals-on-pull-requests/)). When the diff state changed otherwise, each approval becomes `DISMISSED` with its `commit_id` and `submitted_at` kept, and the actor of the change (the pusher, or the user whose edit or merge changed the base) records the issue event `review_dismissed` (prefix `RDE_`, `commit_id` `null`, `dismissed_review` with `state` `approved`, the review ID, `dismissal_message` `null` and the new head as `dismissal_commit_id`) and sends `pull_request_review` `dismissed` (live `mastodon/mastodon` pull request 41811).

T5's `hubdouble_api_pulls::association` is the one `author_association` rule for REST issues, pulls, issue comments, reviews and review comments, for their webhooks, and for GraphQL `authorAssociation` on `Issue`, `IssueComment`, `PullRequest`, `PullRequestReview` and `PullRequestReviewComment`. It answers `OWNER` for the repository owner, `MEMBER` for an active member of the owning organization, `COLLABORATOR` for a repository collaborator, `CONTRIBUTOR` for an account whose pull request merged into the repository or whose commit, matched by email as T4's `hubdouble_api_gitdata::account_by_email` does, reached the default branch, and `NONE` otherwise. The value follows the account's relation now, so an earlier comment changes with it. Live GitHub answers `NONE`, never `FIRST_TIMER` or `FIRST_TIME_CONTRIBUTOR`, for an author with only an open first pull request (`cli/cli` 15111, about 900 sampled pulls in nine repositories), and hubdouble has no mannequin accounts, so those three values never occur (see the fidelity table).

## 6. Contracts frozen in phase 0

A phase 1 agent that needs a change to a contract stops and asks the coordinator, who changes it on `main` for everyone.

### 6.1 Store

```rust
impl Store {
    pub fn view<R>(&self, f: impl FnOnce(&Tx) -> Result<R, ApiError>) -> Result<R, ApiError>;      // shared lock, read only
    pub fn update<R>(&self, f: impl FnOnce(&mut TxMut<'_>) -> Result<R, ApiError>) -> Result<R, ApiError>; // exclusive lock
    pub fn update_quiet<R>(&self, f: impl FnOnce(&mut TxMut<'_>) -> Result<R, ApiError>) -> Result<R, ApiError>; // as update, but the outbox buffer is dropped on commit: the seed load and reset only
    pub fn snapshot(&self) -> Snapshot;           // clones every registered table under the lock (entities are Arcs, so the copy is shallow); taken once after the seed load
    pub fn restore(&self, s: &Snapshot);          // reset: each table's Table::restore(&mut self, seeded: &Self) decides what comes back
}
pub trait Table: Any + Send + Sync + Clone {     // not object safe: the store keeps tables in a TypeId map with typed accessors
    fn restore(&mut self, seeded: &Self) { *self = seeded.clone(); } // default: back to the seeded state
}
pub struct Tx { /* every table, Arc<Config> */ }  // the state inside the lock; only & methods; config() gives the URLs to code that renders outside a request
pub struct TxMut<'a> { /* &'a mut Tx (private), undo log, outbox buffer, id sequence */ } // Deref<Target = Tx>, no DerefMut
impl TxMut<'_> {
    pub fn next_id(&mut self) -> i64;
    pub fn table_mut<T: Table>(&mut self) -> TableMut<'_, T>; // every insert, replace and remove records its undo
    pub fn push_outbox(&mut self, entry: OutboxEntry);        // buffered; reaches the outbox only on commit
}
impl Tx { pub fn table<T: Table>(&self) -> &T; pub fn config(&self) -> &Config; }
pub struct StoreBuilder;                          // register_table::<T>() for every table, then build_with(config) (build() uses Config::default, for tests); no table is added after start
pub struct OutboxEntry { pub app_id: i64, pub installation_id: Option<i64>, pub repo_id: Option<i64>, pub event: &'static str, pub action: Option<&'static str>, pub payload: serde_json::Value, pub redelivery_of: Option<String> }
```

A table overrides `restore` only where section 4.6 keeps state across a reset: the token table keeps every unexpired token of a seeded installation or user, the delivery table keeps the App delivery log, and the counter table (the global ID sequence, delivery IDs, run IDs, each repository's issue and PR number, and the request log cursor) keeps its current values, so every generated sequence keeps counting up. A track's side table uses the default unless 4.6 says otherwise.

`update` commits when the closure returns `Ok`. An `Err` or a panic inside the closure replays the undo log in reverse (every table, side table and ref update) through a drop guard, so a failed or panicking `update` leaves no change and no outbox entry. Outbox entries are handed to the publisher after the lock is released. `Arc` entities are replaced, never mutated in place, so a reader that cloned an `Arc` keeps a stable snapshot.

Frozen entities in `hubdouble-model`, with their fields, in phase 0: `Account` (users, bots and orgs in one ID space), `Membership`, `Team`, `Repo`, `App`, `Installation`, `Token`, `Issue` (issues and PRs share number space and table; PR fields in `Issue.pull`), `IssueComment`, `Review`, `ReviewComment`, `ReviewThread`, `Reaction`, `Label`, `CheckSuite`, `CheckRun`, `Status`, `Release`, `ReleaseAsset`, `WorkflowRun`, `WorkflowJob`, `Ruleset`, `Delivery`. Their tables, with the indexes every track needs (by ID, by repository, by number, by node ID), are in `hubdouble-store`, with `RepoRedirects`, the old `owner/name` of each renamed, transferred or owner-renamed repository, which the REST choke point answers with GitHub's `301` for a read and `307` for a write and GraphQL `repository(followRenames:)` follows, until a new repository takes the name. A track adds fields only through side tables it defines in its own crate, keyed by entity ID and registered on the `StoreBuilder` by its `register` function, never by editing a frozen struct. `Clock` (a trait with `now()`, a system clock and a manual test clock) is in `hubdouble-model`, and every time-dependent rule reads it, so no test waits for real time.

### 6.2 REST router and registry

`cargo xtask gen` builds a segment tree from every OpenAPI path and writes it as static tables into `crates/spec/src/ops_gen.rs`, which is committed, so a normal build reads no OpenAPI file; CI fails when a fresh generation differs. The router splits the escaped path on `/` first and decodes each segment after, so an encoded slash never separates segments: `branches/feature%2Fprotection` is the branch `feature/protection`, not the protection route of `feature` (`GetBranch` and `GetRulesForBranch` send `%2F`, the client's `internal/dispatch/guarded.go:97`); a slash-holding parameter joins its decoded segments with `/`. A literal segment beats a parameter at the same depth. The parameters GitHub allows to hold slashes (`ref`, `path`, `branch`, `basehead`, `tag`) match one or more segments with backtracking, so a route with a literal suffix wins: `commits/{ref}/check-runs`, `/check-suites`, `/status`, `/statuses` and `commits/{commit_sha}/pulls` beat `commits/{ref}`, and `branches/{branch}/protection` beats `branches/{branch}`. A test registers the whole table and checks these pairs and `issues/comments/{comment_id}` against `issues/{issue_number}/events`, plus go-github v93's real escaping for `Repositories.GetContents` and `Git.GetRef` next to the `%2F` branch case. Those escaped paths are literal test data copied from what go-github v93 sends (it escapes each path segment with `url.PathEscape` and keeps `/` between segments), with the go-github source line cited next to each.

```rust
pub struct Grant { pub permission: &'static str, pub access: Access } // GitHub App permission ("contents", "pull_requests", ...)
pub enum Access { Read, Write, Admin }
pub enum Scope { Repo, Org, App /* JWT */, User, Installation, Public }
pub struct Requirement {
    pub any_of: &'static [Grant],         // any one suffices, as GitHub documents per operation; empty for public data
    pub scope: Scope,
    pub scopes: &'static [&'static str],  // classic OAuth scopes
}
pub type Handler = fn(&mut Ctx<'_>) -> Result<Reply, ApiError>;
impl Registry {
    pub fn handle(&mut self, operation_id: &str, req: Requirement, h: Handler); // panics on an unknown or already registered operation
    pub fn extra(&mut self, method: Method, path: &str, operation_id: &'static str, req: Requirement, h: Handler); // routes outside the OpenAPI bundle
    pub fn extra_authenticating(/* as extra */); // the handler checks its own bearer (the Actions runtime token); it runs as Actor::Anonymous
    pub fn extra_writing(/* as extra */); // a GET that changes state (/orgs/{org}/sso records SSO); the server runs it in Store::update
}
```

`operation_id` is GitHub's (`pulls/create`). `extra` registers the routes GitHub serves outside its REST description (`/login/oauth/*`, `/login/device/*`, `/orgs/{org}/sso`) under hubdouble's own operation IDs (`oauth/authorize`), so the choke point, the request log and `hubdouble coverage --inventory` treat them like every other route. GraphQL is not a REST route: `hubdouble-server`, which depends on `gql` and holds every frozen registry, serves `POST /graphql` and its aliases itself, resolves the actor through the same `auth` code, logs the request as operation `graphql`, counts it in coverage, and calls `gql::execute(&gql::Registry, &Store, &Git, &Actor, request)`, which runs a query in one `view` and each mutation in its own `update`, in order. Some operations accept alternative permissions: creating an issue comment takes `issues:write` or `pull_requests:write` ([GitHub](https://docs.github.com/en/rest/issues/comments?apiVersion=2026-03-10#create-an-issue-comment)), and the client relies on the second (`internal/dispatch/assets.go:37`); the tests use a token with each accepted grant and one with neither. `Ctx` gives the path and query parameters, the body (decoded on demand into a `serde` type, a decode error answering GitHub's `400` or `422`), the actor, the resolved repository, the request headers, the `&Git` handle (usable next to the `TxMut`, because the object store is outside the store lock), a `TxMut` for a write operation or a `Tx` for a read (from the HTTP method: `GET` and `HEAD` read, every other method writes), the clock, the base URLs, and `Reply` builders: `json`, `page` (with the `Link` header), `redirect`, `raw`, `empty` and `status`. The `Ctx` lives inside the store transaction, so a handler never locks.

A field without a resolver falls back to the field of the same name in the parent's `serde` form (`#[serde(rename_all = "camelCase")]` on the Rust type registered with `object`), serialized once per parent object and only when a query selects such a field, else a `HUBDOUBLE_NOT_IMPLEMENTED` error on its path. The executor answers a fallback value only when it fits the field's schema type (`null` only where the type is nullable, an enum value of the schema's enum, a scalar's JSON form), else the same error, so a REST spelling never reaches a GraphQL client; `Registry::unchecked_leaves` lists the fallback leaves whose type the executor cannot check, and a test of the whole registry keeps it empty. `Ctx` holds the `Tx`, the `&Git` handle, the actor and `Ctx::load`; `MutCtx` holds the `TxMut` and the same `&Git` at once (`Git` is a separate shared value outside the store lock, so a shared borrow of it and the exclusive borrow of the `TxMut` coexist), with the same `load` (the per-object grant check of section 4.2, backed by P0-D's choke point). Each GraphQL type has one owner, and only the owner calls `object` and `node` for it. Each field has one owner too: P0-B generates `docs/inventory/graphql-fields.tsv` with every `Type.field` the inventory documents select, the coordinator assigns one track to each row in phase 0, `Registry::field` panics on a second registration, and a phase 0 test fails on a row without an owner. The object store is content-addressed and append-only, outside the store lock (a sharded map of `Arc<[u8]>` per fork network); a rolled-back `update` leaves only unreachable objects whose IDs no answer ever gave. Refs live in a store table that P0-C defines and registers on the `StoreBuilder`, so ref changes roll back with everything else. Every `Git` call takes the `Tx` so it can find a repository's fork network through `Repo.fork_of`; inside an `update` or a ref subscriber, pass the `TxMut` itself (`&*tx` through `Deref`), never a second lock. Every ref change goes through `update_ref`. Subscribers run inside the same transaction: P0-C emits `push`, `create` and `delete`; T5 subscribes for `pull_request.synchronize`, PR head oids and `mergeable`; as GitHub does, an open PR's `merge_commit_sha` names its test merge commit from `test_merge` (parents the base it was computed on and the head, the PR author as author, live `cli/cli` PR 15134), computed when the mergeability rule below says, `null` while the merge has a conflict, and T5 keeps `refs/pull/{n}/head` at the head and `refs/pull/{n}/merge` at the test merge through `update_ref`, which sends no event for a `refs/pull/` name; a PR with a conflict keeps its last merge ref (live `cli/cli` PR 15108), and a closed or merged PR keeps `merge_commit_sha` and its head ref and loses its merge ref (live `cli/cli` PR 15128). A closed PR keeps the `mergeable` and `mergeable_state` it had when it closed, also after a later deletion of its head branch, and has `rebaseable` `false` while `mergeable` is known (live `cli/cli` PRs 15127 and 15128, `jqlang/jq` PRs 3708 and 3710, `BurntSushi/ripgrep` PR 3630, `grafana/grafana` PRs 126464 and 132374); a base deletion closes a PR with `mergeable` `false`, `dirty` and `merge_commit_sha` `null` (live `grafana/grafana` PR 137169); a merged PR has `mergeable` `null`, `mergeable_state` `unknown` and `rebaseable` `null` (48 of 48 sampled merges outside a stack in `cli/cli` and `grafana/grafana`). The `refs/pull/` namespace is read-only for clients, as GitHub [documents](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally): T4 refuses a create, update or delete of a `refs/pull/` name through REST `.../git/refs` and GraphQL `updateRefs` with GitHub's `422` `Reference update failed` and the operation's documentation link, before any write. As GitHub does, T5 marks an open PR merged (REST `state: closed` with `merged`, `merged_at`, `merge_commit_sha`; GraphQL `state: MERGED`; `pull_request.closed` with `merged: true`) when an update makes its head reachable from its base; T8 subscribes to create a `check_suite` per App on each pushed head. `PUT /pulls/{n}/merge` and GraphQL `mergePullRequest` (T5) are the other way to merge, with the methods `merge`, `squash` and `rebase`, each refused with `405` when the repository's `allow_merge_commit`, `allow_squash_merge` or `allow_rebase_merge` is off or a ruleset's `allowed_merge_methods` leaves it out. The setting refusals are `Merge commits are not allowed on this repository.`, `Squash merges are not allowed on this repository.` and `Rebase merges are not allowed on this repository.` (public REST answers in `renovatebot/renovate` discussion 23271, GraphQL in `AntoineToussaint/lazybox` issue 469), and the ruleset refusal is the rule refusal `Repository rule violations found` with `{Merge|Squash|Rebase} is not an allowed merge method in this repository.` (Stack Overflow question 79722999). GraphQL `authorEmail` must be the merger's account email or `noreply` address, else the mutation answers `UNPROCESSABLE` `Invalid email address` (`cli/cli` issue 14711), and the address goes into the merger's signature: the author of a merge commit, the author of a squash commit when the merger is the pull request author, and the committer of the rebased commits. A squash writes one commit on the base tip with the tree of the test merge, the PR author as author and GitHub as committer and web-flow signer, and the title and message that the [merge docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/about-pull-request-merges#merge-message-for-a-squash-merge) and the repository's `squash_merge_commit_title` and `squash_merge_commit_message` give, with a `Co-authored-by` trailer for each other commit author (live `helix-editor/helix` PRs 15803 and 16090, `neovim/neovim` PR 42939). A rebase writes one commit per non-merge head commit with its author and message, the merger as committer and no signature (live `helix-editor/helix` PR 15856, `junegunn/fzf` PR 4641). As the [merge docs](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/about-pull-request-merges#rebase-and-merge-your-commits) say, it leaves out the commits that were empty to begin with, and refuses with `405` `This branch can't be rebased` (the message that `chdsbd/kodiak` issue 222 quotes) when a commit does not apply or the rebase is unsafe, that is, when its tree is not the tree of the test merge. The same replay runs with each test merge computation and sets the `Pull` entity's `rebaseable` (`None` until computed, and a `None` beside a known `mergeable` reads as `mergeable`), so REST `rebaseable` and GraphQL `canBeRebased` of an open PR are `false` when a rebase merge would be refused, follow the pending and counted-read rules of `mergeable`, and `canBeRebased` is `false` while `mergeable` is unknown, as its non-null type needs. Both mark the PR merged with `merge_commit_sha` the squash commit or the last rebased commit, as GitHub does. The `Repo` entity holds `squash_merge_commit_title` (`PR_TITLE`, `COMMIT_OR_PR_TITLE`) and `squash_merge_commit_message` (`PR_BODY`, `COMMIT_MESSAGES`, `BLANK`), whose defaults are GitHub's `COMMIT_OR_PR_TITLE` and `COMMIT_MESSAGES`. A fork and its parent share one object store, as a GitHub fork network does, so `object`, `expression` and `compare` on the parent find a commit pushed only to the fork, and refs stay per repository; a pull request from a fork reads its head from the fork's ref (the client compares a fork head through the base repository, `internal/dispatch/review_comparison.go:40`, `internal/router/router.go:851`). A conformance case pushes a commit only to a fork, opens a PR on the parent, and compares it through the parent with the head given both as the fork ref and as the 40-hex head SHA (native review compares SHAs, the client's `internal/reviewadmission/prepare.go:32`). Merges are per path: a path changed on only one side takes that side, a path changed on both sides to different content is a conflict (`ponytail`: line-level merge later if a client needs it).

When mergeability is computed, from live reads on 2026-11-24 and the [pulls docs](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request) ("If the value is `null`, then GitHub has started a background job to compute the mergeability"):

- A head push publishes the new `head.sha` and the live base tip as `base.sha` at once, keeps the last `merge_commit_sha`, and answers `mergeable` `null`, `mergeable_state` `unknown` and `rebaseable` `null` until the computation ends; the test merge is then computed on that `base.sha` and the new head. Live `rust-lang/rust` PR 166365, read 1 s after its push: two reads in a row gave `null`, `unknown`, `null`, the old merge commit and the live tip as `base.sha`, and a read 3 s later gave a new merge commit on that base (`NixOS/nixpkgs` PR 592370 the same). GraphQL gives `mergeable` and `mergeStateStatus` `UNKNOWN` meanwhile (`sharkdp/bat` PR 3832, `grafana/grafana` PR 138721). The `synchronize` webhook carries the pull request as a read at that moment sees it, as do `opened` and `reopened`, which the [octokit examples](https://github.com/octokit/webhooks/tree/main/payload-examples/api.github.com/pull_request) show with `mergeable` `null`, `mergeable_state` `unknown` and `rebaseable` `null`. Opening a PR, reopening it and moving it to another base start the same computation, as the docs say for create and edit, and so does the automatic base change after a merge. The computation keeps the actor whose change started it and sends its move of `refs/pull/{n}/merge` as that actor.
- A base push changes no PR's `base.sha`, `merge_commit_sha`, `mergeable` or `rebaseable`, and REST and GraphQL reads do not change them: 35 open PRs whose base had moved, each read twice, in `cli/cli`, `sharkdp/bat`, `jqlang/jq`, `astral-sh/ruff`, `home-assistant/core` and `microsoft/vscode`, kept a `base.sha` and a test merge from an older base; `sharkdp/bat` PR 4148 kept `base.sha` `dbc11b69` and its merge on it over two days while `master` was four commits ahead. Merged PRs keep that `base.sha` too (`cli/cli` PRs 15142 to 15145). `mergeable_state` reads the live base tip, so 4148 is `behind` though its head contains `dbc11b69`. GitHub computes new test merges on the new base later, keeping `base.sha`, at a time it does not publish (18 `cli/cli` PRs at 2026-11-23T12:56:44Z on `7346a9cb` and none on the five later tips; `sharkdp/bat` PRs at scattered times); the docs name a view of the PR page. A base push still merges a PR whose head it makes reachable, as above.
- hubdouble records a stale PR as a pending computation in the store and runs the test merge out of the push's write: a push signs no commit. While it is pending, the PR answers `null`, `unknown` and `null` (GraphQL `UNKNOWN`). Each REST `pulls/get` and each GraphQL read of `mergeable` or `mergeStateStatus` asks for it through the request's own `ReadJobs`, and the pipeline runs that request's jobs in one write after its reads and before its answer, so each request counts once per PR, whichever other requests run in parallel. The store lock is released between a request's reads and its jobs, so each change that starts a computation gives it a new generation, a read asks with the generation it saw, and its job counts only while that generation is still pending: a read of an older head never counts for a newer push. The read that reaches the repository's count computes the test merge, so the next read answers it. The count is per repository, 2 by default after the live reads above, set by the seed and admin kind `mergeability`; `0` computes in the change itself. A seeded PR is computed at load. `POST /_hubdouble/repos/{owner}/{repo}/pulls/{pull_number}/mergeability` completes a pending computation at once, and on a PR without one computes the test merge on the live base tip and keeps `base.sha`, as GitHub's later computation does. `docs/fidelity.md` lists both differences.

Each track registers the tables, operations, GraphQL types, fields and mutations, ref subscribers, kinds and admin routes for what it owns in its one `register` function; `hubdouble-api::register_all` calls them in the fixed order of section 5, after P0-F's own kinds; kinds apply in that registration order, as section 4.6 states. No crate holds a global registry, a `static` with interior mutability or a `lazy` value a test changes: every registry is built at start and frozen behind an `Arc`, so each test builds its own server.

### How the swarm runs

- One coordinator (the session that owns this plan) starts each agent with a self-contained brief: this plan, the task row, owned paths, the inventory items, and the definition of done.
- Each agent works in its own worktree on its own branch (`p0-b-gql`, `t5-pulls`), commits signed with sign-off, runs `mise run check`, and pushes the branch. The coordinator merges branches into `main` in dependency order, re-runs CI, and removes each worktree and its `target/` once merged.
- Agents do not edit files they do not own. A contract change goes to the coordinator. The files every track appears in, `crates/api/Cargo.toml` and `register_all`, already hold each track's line, written by P0-A, so no track edits them.
- Each worktree has its own `target/` (Cargo's default; no shared or redirected target or cache directory). The dev profile uses `debug = "line-tables-only"` and the test profile builds dependencies with `opt-level = 1`, which keeps each `target/` small and the tests fast; the coordinator runs at most six agents at a time and checks free disk space before it starts each wave.
- Models: phase 0 on `claude-opus-5-5` (provider `claudeAgent`, effort `high`); phase 1 tracks split between `claude-opus-5-5` and `gpt-6.2-sol` (provider `codex`, reasoning effort `high`).

### Engineering rules every agent follows

P0-A writes these into `AGENTS.md`; the workspace lint table and CI enforce what a tool can.

- Lints: `unsafe_code = "forbid"`, Clippy `pedantic` as warnings with `-D warnings` in CI, `unwrap_used` and `expect_used` denied outside tests, `print_stdout` and `dbg_macro` denied; a lint is allowed only on the item that needs it, with `#[expect(..., reason = "...")]`.
- Errors: `thiserror` enums per crate in libraries, `ApiError` at the HTTP edge; no `anyhow` in library crates.
- No code comments beyond `///` doc comments on public items where they add a contract the signature does not show, and `Given`, `When`, `Then` markers in tests. Reasoning goes in commit messages.
- No global mutable state: no `static` with interior mutability, no `OnceLock` or `LazyLock` a test can change; a fixed `Regex` or table may be a `LazyLock` that nothing writes. Timeouts, limits, clocks and environment lookups are fields or parameters, the environment read through a `Fn(&str) -> Option<String>`.
- Tests never wait for real time: the manual `Clock` for wall time, and `#[tokio::test(start_paused = true)]` with `tokio::time` for timers, deadlines and pauses. A test waits on the event it needs (a channel, a drained queue), never on a duration. A test server binds its listener on port 0 before it serves, and an in-process `hyper` service is used where the code takes a connector.
- Tests are independent and run in parallel under `cargo nextest`: no order between tests, no shared fixture a test changes, temporary files only under `tempfile::TempDir`. An expensive shared fixture is a `LazyLock` that no test changes.
- A test asserts behaviour (status, error variant, fields and values), never the wording of a message a person reads. Expected values come from GitHub's behaviour and this plan, never from the code under test.
- Performance: parse an input once and pass the parsed form, avoid per-request allocations on hot paths, and benchmark each hot path with `criterion`.

### Definition of done for a task

- Every listed operation registered with a `Requirement`; every listed GraphQL type, field and mutation registered; every owned event emitted from every cause.
- Tests per operation: success, `404` for an unseen repository, `403` for a missing permission, `422` where the operation validates input, and each response variant.
- Every query parameter and body option the client passes is honoured and tested against records that match only some of it: among them recursive trees (`internal/dispatch/autofix_paths.go:103`), check runs by `check_name`, `app_id` and `filter` (`internal/dispatch/checks.go:88`), workflow runs by `event`, `created`, `status`, `branch` and `head_sha` (`internal/dispatch/work.go:415`), and `per_page` with `page`. The conformance case uses the same options as the client call it mirrors. Response bodies validated against the OpenAPI schema, payloads against the octokit schema, the track's inventory documents executed in conformance.
- `mise run check` green: `cargo fmt --check`, Clippy clean, `cargo deny check`, `cargo nextest run` and doc tests pass, no sleeps or real-time waits in tests, benchmarks for any hot path the track adds.

## 9. Performance targets

Measured by `mise run bench` on one CPU, gated in CI against `main` with a 20 % regression budget.

| Measure | Target |
| --- | --- |
| Image size | under 20 MB |
| Start to ready, fixture seed | under 200 ms |
| Idle memory | under 40 MB RSS, the parsed GraphQL schema included |
| REST `GET` in process | p50 under 100 µs, p99 under 1 ms |
| Inventory GraphQL document | p99 under 3 ms |
| Push to a base branch with 100 open pull requests on it, the client's `updateRefs` document on `main` | p99 under 3 ms, the target of every other write document |
| REST read of a pull request, the first after each such push | p99 under 1 ms, the REST `GET` target |
| Mixed inventory load, reads and writes | over 5 000 requests per second |
| Webhook enqueue | under 20 µs per event |

A push runs no test merge (section 6.4): for each open pull request on the branch the write checks whether the push merged it and, on its base, whether its head is behind the new tip, and on its head records a pending computation. The push row measures that work for 100 pull requests with one worker, and the read row measures a pull request read right after each push. The server uses no thread beyond its `HUBDOUBLE_WORKERS` runtime threads, so one worker is one CPU. Each push moves `main` between two commits, so every push changes the base of all 100 pull requests, and the bench checks that all 100 are open and mergeable before and after.

Measured on the release profile (`lto = "fat"`, `codegen-units = 1`, `panic = "unwind"`, and every loop aligned to 64 bytes by `-C llvm-args=-align-loops=64` in `.cargo/config.toml`, so a change elsewhere in the binary cannot move a hot loop across a fetch boundary and change its speed by 20 % with the same instructions, and the server wraps each handler call in `catch_unwind`, so a panicking handler rolls back and answers `500` without dropping the connection or ending the process). If parsing GitHub's GraphQL schema at start breaks the start target, `xtask gen` precomputes what the executor needs at build time.

The targets hold on the reference runner. A GitHub `ubuntu-latest` runner is not one machine. Ten runners measured the same code in runs 45162472641, 45176261035 and 45188758569, and the raw readings were:

| CPU of the runner | Runners | REST `GET` p50 | Webhook enqueue | Mixed load | Start, client seed | JSON calibration |
| --- | --- | --- | --- | --- | --- | --- |
| Intel Xeon 6975P-C | 1 | 35 µs | 11.6 µs | 8 461 req/s | 137 ms | 54.8 µs |
| AMD EPYC 9V74 | 4 | 85 to 112 µs | 20.2 to 26.1 µs | 5 454 to 7 433 req/s | 170 to 224 ms | 60.4 to 77.5 µs |
| Intel Xeon Platinum 8573C | 4 | 78 to 92 µs | 20.2 to 20.8 µs | 5 705 to 6 058 req/s | 188 to 205 ms | 72.2 to 73.2 µs |
| AMD EPYC 7763 | 1 | 139 µs | 28.6 µs | 5 571 req/s | 219 ms | 76.8 µs |

The same row was up to 4 times slower on one runner than on another, and the runner can change speed during a job: a criterion bench read 79 µs and then 99 µs on the same code in run 45162472641, and 50 µs and 97 µs on two other runners. A raw reading on a slow runner says more about the runner than about the code.

CI judges the targets on the reference runner, the fastest runner in the evidence, the Xeon 6975P-C above. Each run of the targets bench measures a calibration row that uses no hubdouble code, the time to encode and decode a fixed 13 KB JSON document with `serde_json`, before and after the other rows, and keeps the faster of the two. Its factor is that time over 54.8 µs, the time on the reference runner. The gate divides REST `GET` p50 and p99, webhook enqueue and both start times by the factor, multiplies the mixed load by it, and judges the target on the result. The GraphQL document rows, sizes, memory, connections and delivery counts take no factor. A runner faster than the reference has a factor under 1, which makes the check stricter. `mise run bench:targets` on a developer machine judges the raw values.

The scale is an estimate, not a proof. On the ten runners measured, each scaled row divided by its raw value on the reference runner was 1.00 or more: the JSON factor of a runner, 1.10 to 1.41, was not larger than the slowdown of a scaled row on the same runner, which was 1.1 to 4.0. Other runners can differ, and the factor has no upper bound: on a slow runner, a regression of work that does not slow down as much as the calibration can scale to a value under its target. The GraphQL documents take no factor because they do not follow the calibration: on the AMD runners `createCommit` was faster than on the reference runner, and scaling it would have judged it 24 % looser. The factor is the faster of two calibrations, so a slow moment during one of them cannot make it larger.

The regression guard is the paired relative gate, which takes no factor: a head that is more than 20 % slower than the base on the same runner fails on every runner. The absolute gate reads the CPU model that `lscpu` reports, which the workflow logs. On the reference model, `Intel(R) Xeon(R) 6975P-C`, a head that misses a target fails. On any other model, a head that misses a scaled target fails when the base, scaled the same way in the same paired rounds, meets it; when the base misses it too, the gate prints the row as a runner miss with both values and does not fail, because the miss comes from the runner and the relative gate already judged the change. A row the base does not measure, a row without a value, and a row without a factor fail on every model.

The gate is robust to a runner that changes speed during the job. CI builds the base and the head once, then runs the targets bench five times for each, in the order base, head, head, base, base, head, head, base, base, head, each on its own checkout. Round n of the base and round n of the head run next to each other, so a change of speed between rounds reaches both. A row regresses when the median of its five paired changes is over 20 %. Every row, the write documents and the container starts included, is a median of five rounds on both sides, so one slow sample cannot decide it. The section 9 verdict is the median of the five head rounds, each scaled by the factor of its own round. The targets gate fails when it has fewer than five paired rounds, so a manual `mise run bench:gate` on fewer rounds cannot pass. It takes the rows of every round, not of the first pair, and fails when a head report lacks a measure of the table above or the calibration row, when a base report lacks the calibration row, and when a base report lacks a measure that another base report holds; a measure that no base report holds is new on the head. So empty reports cannot pass. The criterion benches take the same design: each bench binary of the base and the head runs five times in the same order, with a 1 s warm up and 1 s of measurement, and a criterion row regresses when the median of its five paired changes of the median time is over 20 %. CI runs every bench binary that either revision has. Before the runs, CI records the benches of each revision with `--list --format terse` in `expected-base.txt` and `expected-head.txt` beside the criterion results, and the gate finds each result by the title in its `benchmark.json`. The criterion gate fails without both lists, when the lists name no bench, when a bench that both revisions list has fewer than five rounds with a readable median on both sides, when the base lists a bench that the head dropped, when a bench that only the head lists has fewer than five readable head rounds, and on a result of a bench that neither list names. A bench that only the head lists is new and is not compared, so a base whose results are all missing or unreadable fails instead of passing as new.
