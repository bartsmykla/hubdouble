# GitHub API fidelity

hubdouble implements the GitHub operations in the [client inventory](inventory/rest-routes.txt). A known REST operation without a handler returns `501`. An unknown REST path returns `404`. See the [implementation plan](PLAN.md#47-fidelity-rules-every-track-follows) for the compatibility contract.

## Differences that clients can see

| Area | hubdouble behavior |
| --- | --- |
| Webhook transport | The server accepts an `https://` webhook URL, but the delivery attempt fails. The receiver gets no request. The attempt log has `status_code: 0`. Use an `http://` receiver for local tests. |
| Webhook queue limit | When 10 000 events or 32 MiB of payload wait for a delivery attempt or are in one, a new event gets no attempt. Its delivery record has `status_code: 0` and the status `Queue full`. Redeliver it when the receiver is back. If more than 8 MiB of such events wait to be logged, the oldest of them are logged without their request, as the webhook delivery retention row says. |
| Webhook response body | The delivery record keeps only the first 4 KiB of the receiver's answer body in `response.payload`. hubdouble does not read the rest. GitHub documents no limit. |
| Webhook delivery memory bound | As GitHub [documents](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/viewing-webhook-deliveries), a delivery older than 3 days by the server's clock leaves `GET /app/hook/deliveries`, and its read and redelivery answer `404`, as live GitHub answers a delivery it no longer keeps (`GET /repos/{owner}/{repo}/hooks/{hook_id}/deliveries/1`, 2026-11-24). To bound memory, hubdouble also keeps the request and response of the newest deliveries of all Apps only up to 8 MiB in total. A delivery of the last 3 days past that bound stays in the list with all its fields, but its read and redelivery answer `404` too. GitHub documents no such bound. |
| Blob text limit | GraphQL `Blob.text` holds at most the first 512 000 bytes of a blob, cut back to the last whole UTF-8 character. `isTruncated` is `true` for a blob larger than that. GitHub documents [`isTruncated`](https://docs.github.com/en/graphql/reference/git#blob) but no limit, and users report text cut near 510 000 characters. Read a truncated blob in full with `GET /repos/{owner}/{repo}/git/blobs/{file_sha}`. |
| Binary patch delta size | `git diff --binary`, as GitHub writes it, makes the raw delta of a side only up to the size of the target deflated at zlib level 1, and writes the delta when it deflates smaller than the target (git v2.47.0 `diff.c`: `emit_binary_diff_body` from line 3327 passes `deflate_size` to `diff_delta` as its limit at lines 3345 to 3347, `deflate_it` at line 3312 deflates at `zlib_compression_level`, and `environment.c` line 46 sets that to `Z_BEST_SPEED`). hubdouble takes the raw delta from libgit2 1.9.7, whose limit is the target deflated at `Z_DEFAULT_COMPRESSION`, level 6, a smaller size (`src/libgit2/patch_generate.c` `create_binary` lines 290 and 302 to 305, `src/util/zstream.c` line 44). A side whose raw delta falls between the two limits is a `literal` in hubdouble and a `delta` in git. Only two encoders make git's delta bytes: git's `diff-delta.c`, which is GPL-2.0 without a linking exception, so hubdouble cannot port it, and libgit2's internal `git_delta`, which has no public API. A call to that function needs `unsafe` code, which the plan forbids (`unsafe_code = "forbid"`, plan section 7 and the workspace lints in `Cargo.toml`). libgit2's public pack builder (`git2::PackBuilder`, git2 0.21.0) gives no such delta either: for the pair of the test, in either insert order, it writes the new blob whole and the old blob as a 72-byte delta against the new one, so it has no delta that makes the new side. The test `a_delta_between_the_libgit2_and_git_caps_is_written_as_a_literal` pins this case with a pair that git writes as a delta. |
| Code owner review requests | As the [docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) say, a pull request that opens ready for review, or a draft that becomes ready, requests a review from each code owner of the files it changes, a team as a team, but not from its author. The docs do not say whether a later push to the head requests the owners of the files it adds, so hubdouble requests no review on a push. A seeded pull request requests no review either. The docs also say that a team's code review assignment can replace the team with some of its members. hubdouble has no review assignment, so it keeps the team. |
| CODEOWNERS size limit | The [docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners) say: "CODEOWNERS files must be under 3 MB in size. A CODEOWNERS file over this limit will not be loaded". They do not say whether 3 MB is 3 000 000 or 3 145 728 bytes. hubdouble loads a file only when it is under 3 145 728 bytes, because GitHub runs on Rails, where `3.megabytes` is 3 × 1 048 576 bytes. A file of 3 000 000 to 3 145 727 bytes is loaded by hubdouble and may not be by GitHub. |
| Release asset download | After the access check, a download with `Accept: application/octet-stream` answers `302` to an unguessable signed `/_blobs/` URL on hubdouble that works until 300 seconds after the redirect by the server's clock. Live GitHub redirects to `release-assets.githubusercontent.com` with an Azure SAS (`se` up to an hour away, no `st`) and a `jwt` whose `nbf` to `exp` is 300 seconds (`cli/cli` asset 761188502, 2026-11-25). hubdouble keeps the expiry in `se` and `sig` and has no `jwt` parameter. `sig` stands for the token and `se` for its `exp` claim. An expired link answers the CDN's `618`, a link without `sig` `618` as a token not provided, and a link without `se` or with another signature `618` as a failed signature, each with `Content-Type: application/octet-stream`, or `text/html; charset=utf-8` when the link has no query (live sends the `response-content-type` of the link, and `text/html` without a query), each with the Varnish error page and, over HTTP/1.1, the status line `jwt:expired`, `jwt:jwt-not-provided` or `jwt:signature-fail`, as live answered on a cache miss. Live puts the token in the `jwt:signature-fail` status line, and a public asset in the CDN cache is served even without the token. hubdouble has no cache. |
| Actions job log download | After the access check, hubdouble redirects to an unguessable signed `/_blobs/` URL with `st`, `se` and `sig`, as GitHub redirects to an Azure Blob Storage URL. The link works until 10 minutes after the redirect by the server's clock: the [docs](https://docs.github.com/en/rest/actions/workflow-jobs#download-job-logs-for-a-workflow-run) say one minute, but live links set `se` 10 minutes after the request (`cli/cli` job 138283445124, 2026-11-24). The signature covers `st` and `se`. A link read before `st` or after `se`, a link without `se` and a link with another signature answer the storage's `403` with `x-ms-error-code: AuthenticationFailed`, its XML error and, over HTTP/1.1, its status line, as the live link did (2026-11-25). Over HTTP/2 the status line has no text. The detail for another signature is `Signature did not match.` without Azure's string to sign, because that string names Azure's account and container. |
| Re-run past the 50 re-run limit | GitHub [says](https://github.blog/changelog/2026-04-10-actions-workflows-are-limited-to-50-reruns/) that a re-run past the limit gives "a failed check suite with an annotation", but the annotation text and what happens to the attempt are not public. hubdouble answers `201` and adds an attempt that completes at once with conclusion `failure` and no jobs. The run's check suite completes with `failure`. The suite gets no new check run and no annotation, because the REST API reads annotations only from check runs. The `statusCheckRollup` reads only check runs and statuses, so it does not show that failure. |
| The `github` organization | `GET /users/github` and `GET /user/9919` give the organization that owns GitHub Actions with the profile of live GitHub. Its `public_repos` and `followers` count hubdouble's data, so both are `0`. A seeded account with the login `github` or the ID 9919 replaces it on both routes. When one seeded account holds the login and another the ID, the one with the login owns GitHub Actions in every check run and suite, as `GET /users/github` gives it, and `GET /user/9919` gives the other. |
| Check suite on a commit that no push made a ref tip | A check suite on a commit that no push made the tip of a branch or tag, such as an inner commit of a push of several commits, has `before` and `after` as `null`. GitHub does not document these values. Live GitHub gives `null` for both on the suite of a fork's head in the base repository, which no push to that repository made a ref tip (`cli/cli` suite 121957565167). No live sample of an inner commit was read. |
| Check run states that only GitHub sets | The [check run docs](https://docs.github.com/en/rest/checks/runs#create-a-check-run) say that only GitHub Actions sets the `status` `waiting`, `requested` or `pending`, and only GitHub sets the `conclusion` `stale`. The write schemas also leave out `startup_failure`. GitHub documents no answer for an App that sends one, and no public record of the answer was found. hubdouble answers an App's create or update with `422` `Validation Failed` and an `invalid` error on the `CheckRun` field `status` or `conclusion`, and keeps the run as it was. GitHub Actions' own check runs and the seed can hold these states. |
| GraphQL error type of a branch rule refusal | GitHub publishes no GraphQL error type for a rule refusal of `updateRefs` or `createCommitOnBranch`, and public reports quote only the message `Repository rule violations found`. hubdouble answers it as an `UNPROCESSABLE` error with the same message as the REST refusal. |
| Tree deletion of an absent path | GitHub's docs say that `POST /repos/{owner}/{repo}/git/trees` returns an error when an entry with `sha: null` deletes a file that does not exist, but they give no status or message. hubdouble answers `422` with a validation error on `tree.sha`. |
| Git tree depth | GitHub recommends a maximum of 50 directory levels. hubdouble enforces the limit to protect recursive tree operations. The Git Trees API returns `422` for a deeper tree. |
| Webhook ID | A webhook payload or delivery record with a `hook_id` uses the App ID as that value. The `X-GitHub-Hook-ID` header also uses the App ID. |
| Admin writes | Most seed kinds have no direct update or delete route. An unsupported admin method and path return `404`. See the [admin route list](admin-api.md). |
| Rename redirect of a write | A write to an old repository name answers `307` with `Location` and the body of the `301`, with the message `Temporary Redirect`, as GitHub's [repository redirects announcement](https://developer.github.com/changes/2015-04-17-preview-repository-redirects/) says ("a 301 or 307 HTTP redirect, depending on the type of request"). The pinned description lists `307` only for `PATCH` and `DELETE /repos/{owner}/{repo}`. A live sample needs a write to GitHub, so the status and the message are not checked. |
| Comment edit and delete refusal | The author of an issue comment or a review comment, a user with write access, and an installation with the operation's write permission can edit or delete it, as GitHub [documents](https://docs.github.com/en/communities/moderating-comments-and-conversations/managing-disruptive-comments). GitHub publishes no status or message for other users. hubdouble answers `403` with `Must have push access to repository` for both comment kinds. |
| Installation team and collaborator reads | GitHub [lists](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps) the organization `members` read permission for the team reads and repository `metadata` read for collaborator permission, but documents no answer for an installation outside the organization. hubdouble treats an installation on another account as a user who is not a member: `GET /orgs/{org}/teams` answers `403` and a team read answers `404`. An installation with `metadata` read reads collaborator permission and `Repository.collaborators` without the push access check that users need. |
| Repository permissions | Standard REST repository responses omit `permissions` for anonymous callers, App JWTs, and installation tokens. User and personal tokens can receive the viewer's `permissions`. The team repository media type reports the team's permissions. |
| OAuth client authentication | `POST /login/oauth/access_token` reads `client_id` and, for grants that require it, `client_secret` from the body. An HTTP Basic header has no effect. Basic credentials alone return the OAuth error `incorrect_client_credentials`. |
| Private team repositories | A classic personal token with `admin:org` but without `repo` gets `404` when it checks access to a private team repository. |
| Search types | Only GraphQL issue search, which also returns pull requests, has a handler. `ISSUE`, `ISSUE_ADVANCED`, and `ISSUE_HYBRID` use the same search. Other GraphQL search types return `HUBDOUBLE_NOT_IMPLEMENTED`. REST search operations return `501`. |
| Search text matching | GitHub publishes no text analyzer. In live `atom/language-toml` searches, `spec` found `specs` but not `specific`, `specs` did not find `spec`, and `fix` found `fixed` and `fixes`. hubdouble matches whole words, and a word in the text also matches as its Snowball English stem. A query word is not stemmed. GitHub may drop stop words or use another stemmer, which no sample showed. |
| Search order | Without `sort:`, GitHub orders by best match, which it does not publish. hubdouble orders by creation time, newest first, which live GitHub also gave for every sampled query without text. GitHub publishes no order for ties in a sort by comments, reactions or interactions. hubdouble puts the newest item first for descending sorts and the oldest first for ascending sorts. The docs make `sort:reactions-+1` and `sort:reactions-+1-asc` ascending, but live GitHub gave descending order for both, while `sort:reactions-asc` was ascending. hubdouble sorts by one reaction kind in descending order with or without `-asc`. The sampled repository has no other reaction kind to tell the order apart. |
| Search interactions | hubdouble counts interactions as live GitHub gave them for the 40 issues and 38 of the 43 pull requests that `cli/cli` opened from 2026-11-16 to 2026-11-23: the issue comments, review comments and submitted reviews with a body, plus the reactions on the issue or pull request itself. Reactions on comments do not count. `comments:` counts the same comments. 4 other pull requests had a lower live value, which looks like index lag. Pull request 15071 had one more, as GraphQL `totalCommentsCount` also gave, and its comments, reviews and threads do not show what the extra item is. Live GitHub also has no value for many issues last updated before 2025-09-05, so `interactions:>=1` leaves them out and an interactions sort puts them last. hubdouble has no index, so every item has its current value. |
| Search qualifiers without data | hubdouble has no milestones, projects or merge queue. `milestone:`, `project:` and `is:queued` find nothing, and `no:milestone` and `no:project` match every item. |
| Search closing links | `linked:pr` and `linked:issue` use the closing keywords of pull requests on the default branch and the manual links, as `closedByPullRequestsReferences` does. Live `atom/language-toml` pull requests 9 and 12 have `Fixes #8` and `Fixes #11` in their bodies but no closing references, and GitHub publishes no reason. |
| Closing link limit | GitHub documents a limit of ten links per pull request. If the seed and body supply more, Hubdouble keeps manual links first and uses issue ID order within each group. GitHub does not document this selection order. |
| GraphQL reopen refusal | A refused reopen through GraphQL `reopenPullRequest` answers `Could not open the pull request.` for every reason. Public reports give that text for a deleted base branch ([VdustR/skills#54](https://github.com/VdustR/skills/issues/54)) and for a head that is no longer a descendant of the stored head ([isaacs/github#361](https://github.com/isaacs/github/issues/361)), and no other text, but none covers a merged pull request or a duplicate open pull request. |
| Failed automatic retarget | When a merge deletes its head branch, GitHub records `automatic_base_change_failed` on a merged pull request based on that branch (live `getsentry/sentry` pull requests 132051 and 132005). GitHub publishes no sample for an open or a closed unmerged pull request whose move fails, such as an open one onto a base that another open pull request from the same head targets, or an open one whose head branch was deleted through the API. hubdouble records `automatic_base_change_failed` for each such move too, and the deletion then closes an open one as it closes every open pull request on a deleted base. |
| Pull request ref writes | GitHub [documents](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally) the `refs/pull/` namespace as read-only and refuses a `git push` to it with `deny updating a hidden ref`, but publishes no answer for a write through the API. hubdouble refuses a create, update or delete of a `refs/pull/` name through REST `.../git/refs` with `422` and `Reference update failed`, GitHub's [refusal](https://github.com/renovatebot/renovate/discussions/33761) for a ref update that fails, and through GraphQL `updateRefs` with an `UNPROCESSABLE` error. |
| Mergeability computation time | GitHub computes mergeability in a background job and publishes no duration. Two reads right after a head push answered `mergeable: null` and a read 3 s later answered the value (live `rust-lang/rust` pull request 166365 and `NixOS/nixpkgs` pull request 592370). hubdouble has no background job and counts reads instead: after a change that makes mergeability stale, the next `reads` reads answer `null` (2 by default, set by the [`mergeability`](seed.md#mergeability) kind), and the work runs right after the last of them. A read is the REST pull request read or a GraphQL read of `mergeable` or `mergeStateStatus`. `POST /_hubdouble/repos/{owner}/{repo}/pulls/{pull_number}/mergeability` ends the wait at once. |
| Test merge after a base push | A base push changes no pull request's `base.sha`, `merge_commit_sha`, `mergeable` or `rebaseable`, and REST and GraphQL reads do not change them either (35 open pull requests whose base had moved, each read twice with REST and GraphQL, in `cli/cli`, `sharkdp/bat`, `jqlang/jq`, `astral-sh/ruff`, `home-assistant/core` and `microsoft/vscode`, and `sharkdp/bat` pull request 4148 over two days). GitHub later computes new test merges on the new base and keeps `base.sha`, at a time it does not publish: 18 open `cli/cli` pull requests got a test merge on `7346a9cb` at 2026-11-23T12:56:44Z or a second later, and none on the five later tips, while `sharkdp/bat` pull requests got theirs at scattered times. The docs name a view of the pull request page as one cause. hubdouble has no web pages, so it keeps the snapshot until the next head push, base change or reopen, or until the admin route above computes it. |
| Merge state values | `mergeable_state` and GraphQL `mergeStateStatus` never give `has_hooks` or `draft`. The [GraphQL schema](https://docs.github.com/en/graphql/reference/enums#mergestatestatus) gives `HAS_HOOKS` for "passing commit status and pre-receive hooks", which only GitHub Enterprise Server runs, and hubdouble runs no pre-receive hooks. The schema marks `DRAFT` deprecated, and live GitHub answered another state for each of about 60 sampled drafts (`jqlang/jq` pull request 3750 `clean`, `cli/cli` pull request 14927 `blocked`). hubdouble answers a draft as a ready pull request. |
| Author association values | `author_association` and GraphQL `authorAssociation` never give `FIRST_TIMER`, `FIRST_TIME_CONTRIBUTOR` or `MANNEQUIN`. In about 900 sampled pull requests in nine repositories, among them `cli/cli`, `golang/go` and `firstcontributions/first-contributions`, live GitHub gave an author with only an open first pull request `NONE` (`cli/cli` pull request 15111), also in the `opened` webhook ([community discussion 78038](https://github.com/orgs/community/discussions/78038)). A mannequin is a placeholder for an unclaimed user that an import makes, and hubdouble has no imports. |
| Pull request state order | `Issue.closedByPullRequestsReferences` accepts `orderByState`. The argument has no effect. The [GitHub schema](https://docs.github.com/en/graphql/reference/issues#issue) gives no sort direction, and the client omits the argument. |
| Commit status context case | GitHub's docs say that a status `context` is case-insensitive, but publish no answer for two statuses whose contexts differ only in case, and no public sample was found. hubdouble counts them as one context: the combined status lists the newest of them with the spelling that it was created with, and a required status check of either spelling reads it. |
| Diff and patch object IDs | Live GitHub abbreviates `index` IDs with git's automatic length for the object count of the repository network: 12 characters for `octocat/Spoon-Knife`, 10 for `octocat/linguist`. hubdouble applies the same rule to its own network, so a small seeded repository gets 7. hubdouble cannot hold GitHub's object count. |
| Hunk function context | Live GitHub picks a function-name pattern by language: a Ruby `def` line heads a hunk in `octocat/linguist` commit 17168d5. GitHub publishes no mapping from files to patterns, so hubdouble uses git's default rule for every file: the nearest earlier line that starts with a letter, `_` or `$`, cut at 80 bytes. The same text is in each JSON `patch`. |
| Typed dispatch inputs | GitHub refuses a `choice` value outside `options` and a `boolean` value other than `true` or `false` with `Provided value '...' for input '...' not in the list of allowed values`, and an array value with `Invalid value for input '...'` (cli/cli issue 5246, ROCm/TheRock issues 3634 and 5749, convictional/trigger-workflow-and-wait issue 98). GitHub publishes no check of a `number` or `environment` value, and a `number` input started a run with the value `a` (pakapaka.jp, 2026-10-09), so hubdouble accepts any value for both. GitHub publishes no rule for a JSON number or boolean sent for an input, so hubdouble reads it as its text. GitHub does not publish which input it names when several fail. hubdouble names the first in name order. |
| Commit status validation body | Live answers quoted in 2026 for a long `description` and a `target_url` without an `http` or `https` scheme have `message`, `errors` as one string and `status`, and no `documentation_url` (renovatebot/renovate issue 44119, projectbluefin/lab issue 471), and hubdouble answers so. The order of the two texts when both fail is not public; hubdouble names the description first. |
| An `Accept` range that is not a media type | Live GitHub reset the connection for `Accept: foo` and then refused new connections from the address for some minutes (2026-11-24). That block belongs to GitHub's network edge, not to the API, and hubdouble has none, so it answers such a range with the `415` of every unsupported range. |
| Issue lock refusals | GitHub publishes no answer for a `lock_reason` outside its four values, for a lock of a locked issue or for an unlock of an unlocked one, and a live sample needs a write. hubdouble answers the wrong reason with `422`, `Validation Failed` and an `invalid` error on the `Issue` field `lock_reason` with the value. A lock with the reason the issue already has, or an unlock of an unlocked issue, answers `204` and changes nothing, so no event is recorded or sent. A lock with a new reason locks again and records and sends `locked`. |
| Issue event types | `GET .../issues/{n}/events` lists the [event types](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types) that hubdouble's writes make, with the fields of a live sample (2026-11-25). The other types come from writes that hubdouble does not serve, such as milestones, pins, transfers, deployments, projects, blocks and duplicates, or are timeline events, and hubdouble serves no timeline. |
| Installation list `since` | The [installation list docs](https://docs.github.com/en/rest/apps/apps#list-installations-for-the-authenticated-app) describe `since` with the same text as the comment lists and publish no boundary. A live read needs an App's JWT. hubdouble reads `since` as the comment lists do: Ruby's `Time.parse` in Pacific time, a `422` with the comment lists' message for a time that it cannot read, and an installation updated at or after the time, with the microseconds kept. |
| Push rule refusal texts | Public refusals show only `File path is restricted` (git push `GH013` in `google-gemini/gemini-cli` 25123 and `renovatebot/renovate` 44819). For the other push rules, hubdouble uses `File extension is restricted`, `File size is too large` and `File path is too long`. A refusal through the REST API takes the form of the branch rule refusals. |
| Tag rule refusal texts | Public refusals show `Cannot delete this tag`, `Cannot force-push to this tag` and `Cannot update this protected ref.` for tags. For a tag creation, signatures and linear history, hubdouble uses the texts of the same branch rules. |
| Default branch deletion through GraphQL | GitHub's REST refusal is `422` `Cannot delete the default branch`. No public GraphQL sample shows it. hubdouble answers `updateRefs` with `UNPROCESSABLE` and the same text. |
| Code owner review refusal | Public samples show one owner set: `Waiting on code owner review from A, B, and/or C.`, before the check violations. When the changed files have more than one owner set without an approval, hubdouble gives one such line for each set, in the order of the changed paths. Owners without write access are not named. |
| Workflow change in a merge | GitHub refuses a push that changes a workflow file without the right. No public sample shows `POST /merges` or `PUT .../pulls/{n}/merge` with such a change. hubdouble answers `403` with the push text, as the update-branch merge answers `403` (`limitlessprojects/Go-Hybrid` 762). |
| Write and directory headers | A live GET cannot show the headers of a REST write. hubdouble sends a write the headers of a non-GET answer, as live `POST /graphql` does: no `Cache-Control` and `Vary: Accept-Encoding, Accept, X-Requested-With`. A directory contents read answers a strong tag that is not the tree SHA and is the same for two directories of one commit (`cli/cli` `/` and `/docs`); hubdouble answers the tag of the body. The `Last-Modified` of a live issue, pull request or label read is a time that its body does not show (`cli/cli` issue 1 sends a time after its `updated_at`); hubdouble sends `updated_at` for an issue or pull request and no time for a label. |
| Conversation lock | `PUT .../issues/{n}/lock` by a user without write access answers `403` `Must have push access to repository.`; no public sample shows the text. `addPullRequestReviewThread` on a locked pull request answers `FORBIDDEN` with the REST text; no public GraphQL sample shows it. |
GitHub documents redirect responses for the [repository endpoint](https://docs.github.com/en/rest/repos/repos#get-a-repository).

## REST, IDs, and commits

- A repository keeps each old owner and name of a rename, a transfer and an owner login rename. A read by an old name, in any case, answers `301` with `Location` and a body `url` of `/repositories/{id}` plus the rest of the path and the query, the message `Moved Permanently` and the [follow redirects](https://docs.github.com/rest/guides/best-practices-for-using-the-rest-api#follow-redirects) link, as live `repos/twitter/bootstrap` does. An old name of a repository that the actor cannot see answers `404`. A new repository with an old name takes the name back. GraphQL `repository` follows an old name unless `followRenames` is `false`, which answers `NOT_FOUND`.
- Errors use `message`, `documentation_url`, and a string `status`. A validation error can include `errors` entries with `resource`, `field`, and `code`.
- Page-based lists accept `page` and `per_page` (default 30, maximum 100). Responses include `Link` when there are other pages. A `Link` repeats each query name once, with its last value. Operations with cursors, such as App deliveries, use cursor pagination. An empty list is `[]`.
- A page list answers `422` when `page * per_page` is larger than `9223372036854775807`. The repository issue list without `after` or `before` answers `422` when `page * (per_page + 1)` is larger than 10 000, the repository comment list past 30 000 results, releases past 10 000 and workflow runs past 40 000.
- Successful API GET responses use a strong `ETag` derived from the media type and response body; a file read uses its blob SHA, as on GitHub. A match with `If-None-Match`, weak or strong, returns `304` with the strong tag.
- A client that accepts `gzip` gets JSON and `text/plain` bodies of 20 bytes or more compressed, with the weak form of the tag, except a contents read; live GitHub compressed a 23-byte body and left a 12-byte one alone.
- A successful GET or HEAD, and its `304`, sends `Cache-Control: private, max-age=60, s-maxage=60` to an authenticated caller and `public, ...` to an anonymous one (`86400` for a blob read), with GitHub's `Vary` for that class; a `304` to an anonymous caller keeps its `Content-Type`. Other answers send no `Cache-Control` and `Vary: Accept-Encoding, Accept, X-Requested-With`, and anonymous GraphQL sends no `Vary`.
- A repository, user, release, issue, pull request or reference read sends `Last-Modified` with the update time of the repository or the item; a file or commit read sends the committer time of its commit, a directory read the update time of the repository, and a commit list the time of its first listed commit. `If-Modified-Since` in any HTTP date form at or after that time answers `304`, unless the request sends `If-None-Match`.
- API responses include GitHub request, media type, version, and rate-limit headers. Rate-limit counters are fixed and the remaining count stays above zero unless a fault overrides it, except for anonymous GraphQL, whose limit is `0` as on GitHub. User tokens can receive `X-OAuth-Scopes`.
- The REST API accepts `X-GitHub-Api-Version` values `2022-11-28` and `2026-03-10`. It defaults to `2022-11-28` and returns `400` for other versions. GraphQL ignores the header and sends no `X-GitHub-Api-Version-Selected`, and its `X-GitHub-Media-Type` defaults to `github.v4`.
- New object IDs use a server-wide signed 64-bit sequence. An explicit admin ID at or below that sequence returns `422`. Current GraphQL node IDs have a type prefix and an opaque payload. For a resolved legacy base64 ID, GraphQL returns a `DEPRECATION` warning in `extensions` with `next_global_id`.
- Timestamps use RFC 3339 in UTC with second precision. Reads of an unchanged Git ref return the same target.
- The App delivery log retains the last 50,000 attempts per App.
- Merge and squash commits and commits from `createCommitOnBranch` use committer `GitHub <noreply@github.com>` and the local web-flow key. Rebase merge commits have the merger as committer and no signature. Installation-token Git data commits without an author, committer, or signature use the same key. They report `verification.verified: true` and reason `valid`. Client-signed Git data commits report `unknown_key`. Other unsigned commits report `unsigned`.

## GraphQL

- The validation exception in the plan allows fields with the same response name to differ in nullability on mutually exclusive concrete types. The `originalCommentEdit` inventory document uses this for `pullRequest` on `IssueComment` and `PullRequestReviewComment`.
- A null from a failed non-null field propagates to the nearest nullable parent. GraphQL errors give a `type`, and execution errors identify the field with a `path` and source `locations`.
- The schema is GitHub's live introspection, pinned in `spec/graphql/` by `mise run graphql:pin`: the body of `GET /graphql` and the facts that only an introspection `POST` shows. `spec/graphql/schema.graphql` is generated from the two pins, and a test fails when it differs from them. An authenticated `GET /graphql` answers the pinned body byte for byte, with the `graphql` rate-limit resource and `X-Accepted-OAuth-Scopes: repo`. `__schema`, `__type` and `__typename` in a posted document answer from the same pins.
- A GraphQL answer keeps the order of the selection.
- Connections require `first` or `last`, with a maximum of 100. An unimplemented field returns `HUBDOUBLE_NOT_IMPLEMENTED` on its path. A repository the caller cannot see returns null with `NOT_FOUND` for that alias.

## Test controls

Use [admin faults](admin-api.md#state-request-log-and-faults) to substitute a response, such as a secondary rate limit, `502`, or an `X-GitHub-SSO` header. The rule controls the match, status, body, headers, delay, and count.

Workflow dispatch creates a run and its jobs. The double simulates run state and can issue a run token. It does not execute workflow jobs. Use the Actions admin routes or the seed's `auto_complete` option to control run state. A job patch in the Actions admin route can append `annotations` to the job's check run, in the form that the Checks API takes them.
