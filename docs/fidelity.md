# GitHub API fidelity

hubdouble implements the GitHub operations in the [client inventory](inventory/rest-routes.txt). A known REST operation without a handler returns `501`. An unknown REST path returns `404`. See the [implementation plan](PLAN.md#47-fidelity-rules-every-track-follows) for the compatibility contract.

## Differences that clients can see

| Area | hubdouble behavior |
| --- | --- |
| Webhook transport | The server accepts an `https://` webhook URL, but the delivery attempt fails. The receiver gets no request. The attempt log has `status_code: 0`. Use an `http://` receiver for local tests. |
| Webhook queue limit | When 10 000 events or 32 MiB of payload wait for a delivery attempt or are in one, a new event gets no attempt. Its delivery record has `status_code: 0` and the status `Queue full`. Redeliver it when the receiver is back. If more than 8 MiB of such events wait to be logged, the oldest of them are logged without their request, as the webhook delivery retention row says. |
| Webhook response body | The delivery record keeps only the first 4 KiB of the receiver's answer body in `response.payload`. hubdouble does not read the rest. GitHub documents no limit. |
| Webhook delivery retention | GitHub keeps deliveries for 3 days and then removes them. hubdouble keeps the request and response of the newest deliveries of all Apps up to 8 MiB in total. An older delivery stays in `GET /app/hook/deliveries` with all its fields. A read of it with `GET /app/hook/deliveries/{id}` and a redelivery of it return `404`, as for a delivery that GitHub no longer keeps. |
| Blob text limit | GraphQL `Blob.text` holds at most the first 512 000 bytes of a blob, cut back to the last whole UTF-8 character. `isTruncated` is `true` for a blob larger than that. GitHub documents [`isTruncated`](https://docs.github.com/en/graphql/reference/git#blob) but no limit, and users report text cut near 510 000 characters. Read a truncated blob in full with `GET /repos/{owner}/{repo}/git/blobs/{file_sha}`. |
| Release asset download | A download with `Accept: application/octet-stream` answers `302` to an unguessable `/_blobs/` URL on hubdouble, after the access check. GitHub redirects to a signed URL that expires after a few minutes. The hubdouble URL does not expire. |
| Actions job log download | After the access check, hubdouble redirects to an unguessable `/_blobs/` URL with no time limit. GitHub's URL expires after one minute. |
| Re-run past the 50 re-run limit | GitHub [says](https://github.blog/changelog/2026-04-10-actions-workflows-are-limited-to-50-reruns/) that a re-run past the limit gives "a failed check suite with an annotation", but the annotation text and what happens to the attempt are not public. hubdouble answers `201` and adds an attempt that completes at once with conclusion `failure` and no jobs. The run's check suite completes with `failure`. The suite gets no new check run and no annotation, because the REST API reads annotations only from check runs. The `statusCheckRollup` reads only check runs and statuses, so it does not show that failure. |
| The `github` organization | `GET /users/github` and `GET /user/9919` give the organization that owns GitHub Actions with the profile of live GitHub. Its `public_repos` and `followers` count hubdouble's data, so both are `0`. A seeded account with the login `github` or the ID 9919 replaces it on both routes. When one seeded account holds the login and another the ID, the one with the login owns GitHub Actions in every check run and suite, as `GET /users/github` gives it, and `GET /user/9919` gives the other. |
| Check suite on a commit that no push made a ref tip | A check suite on a commit that no push made the tip of a branch or tag, such as an inner commit of a push of several commits, has `before` and `after` as `null`. GitHub does not document these values. Live GitHub gives `null` for both on the suite of a fork's head in the base repository, which no push to that repository made a ref tip (`cli/cli` suite 121957565167). No live sample of an inner commit was read. |
| Check run states that only GitHub sets | The [check run docs](https://docs.github.com/en/rest/checks/runs#create-a-check-run) say that only GitHub Actions sets the `status` `waiting`, `requested` or `pending`, and only GitHub sets the `conclusion` `stale`. The write schemas also leave out `startup_failure`. GitHub documents no answer for an App that sends one, and no public record of the answer was found. hubdouble answers an App's create or update with `422` `Validation Failed` and an `invalid` error on the `CheckRun` field `status` or `conclusion`, and keeps the run as it was. GitHub Actions' own check runs and the seed can hold these states. |
| GraphQL error type of a branch rule refusal | GitHub publishes no GraphQL error type for a rule refusal of `updateRefs` or `createCommitOnBranch`, and public reports quote only the message `Repository rule violations found`. hubdouble answers it as an `UNPROCESSABLE` error with the same message as the REST refusal. |
| Tree deletion of an absent path | GitHub's docs say that `POST /repos/{owner}/{repo}/git/trees` returns an error when an entry with `sha: null` deletes a file that does not exist, but they give no status or message. hubdouble answers `422` with a validation error on `tree.sha`. |
| Git tree depth | GitHub recommends a maximum of 50 directory levels. hubdouble enforces the limit to protect recursive tree operations. The Git Trees API returns `422` for a deeper tree. |
| Webhook ID | A webhook payload or delivery record with a `hook_id` uses the App ID as that value. The `X-GitHub-Hook-ID` header also uses the App ID. |
| Admin writes | Most seed kinds have no direct update or delete route. An unsupported admin method and path return `404`. See the [admin route list](admin-api.md). |
| Repository renames | The old owner and name return `404` through REST, with no `301` redirect. GraphQL accepts the schema's `followRenames` argument but has no rename lookup. An old name returns a null repository with `NOT_FOUND`, regardless of that argument. |
| Comment edit and delete refusal | The author of an issue comment or a review comment, a user with write access, and an installation with the operation's write permission can edit or delete it, as GitHub [documents](https://docs.github.com/en/communities/moderating-comments-and-conversations/managing-disruptive-comments). GitHub publishes no status or message for other users. hubdouble answers `403` with `Must have push access to repository` for both comment kinds. |
| Installation team and collaborator reads | GitHub [lists](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps) the organization `members` read permission for the team reads and repository `metadata` read for collaborator permission, but documents no answer for an installation outside the organization. hubdouble treats an installation on another account as a user who is not a member: `GET /orgs/{org}/teams` answers `403` and a team read answers `404`. An installation with `metadata` read reads collaborator permission and `Repository.collaborators` without the push access check that users need. |
| Repository permissions | Standard REST repository responses omit `permissions` for anonymous callers, App JWTs, and installation tokens. User and personal tokens can receive the viewer's `permissions`. The team repository media type reports the team's permissions. |
| OAuth client authentication | `POST /login/oauth/access_token` reads `client_id` and, for grants that require it, `client_secret` from the body. An HTTP Basic header has no effect. Basic credentials alone return the OAuth error `incorrect_client_credentials`. |
| Private team repositories | A classic personal token with `admin:org` but without `repo` gets `404` when it checks access to a private team repository. |
| Search types | Only GraphQL issue search, which also returns pull requests, has a handler. `ISSUE`, `ISSUE_ADVANCED`, and `ISSUE_HYBRID` use the same search. Other GraphQL search types return `HUBDOUBLE_NOT_IMPLEMENTED`. REST search operations return `501`. |
| Negated search qualifiers | A qualifier such as `-author:octocat` acts as a text term. It does not exclude matches. |
| Search in comments | Text search checks titles and bodies. `in:comments` alone with a text term finds no matches. If you also specify `title` or `body`, the search uses those fields. |
| Search order | `sort:created` and `sort:updated` support ascending and descending order. Sorts by comments, reactions, or interactions have no effect. The default order is creation time, newest first. |
| GraphQL reopen refusal | A refused reopen through GraphQL `reopenPullRequest` answers `Could not open the pull request.` for every reason. Public reports give that text for a deleted base branch ([VdustR/skills#54](https://github.com/VdustR/skills/issues/54)) and for a head that is no longer a descendant of the stored head ([isaacs/github#361](https://github.com/isaacs/github/issues/361)), and no other text, but none covers a merged pull request or a duplicate open pull request. |
| Failed automatic retarget | When a merge deletes its head branch, GitHub records `automatic_base_change_failed` on a merged pull request based on that branch (live `getsentry/sentry` pull requests 132051 and 132005). GitHub publishes no sample for an open or a closed unmerged pull request whose move fails, such as an open one onto a base that another open pull request from the same head targets, or an open one whose head branch was deleted through the API. hubdouble records `automatic_base_change_failed` for each such move too, and the deletion then closes an open one as it closes every open pull request on a deleted base. |
| Pull request ref writes | GitHub [documents](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/checking-out-pull-requests-locally) the `refs/pull/` namespace as read-only and refuses a `git push` to it with `deny updating a hidden ref`, but publishes no answer for a write through the API. hubdouble refuses a create, update or delete of a `refs/pull/` name through REST `.../git/refs` with `422` and `Reference update failed`, GitHub's [refusal](https://github.com/renovatebot/renovate/discussions/33761) for a ref update that fails, and through GraphQL `updateRefs` with an `UNPROCESSABLE` error. |
| Mergeability computation time | GitHub computes mergeability in a background job and publishes no duration. Two reads right after a head push answered `mergeable: null` and a read 3 s later answered the value (live `rust-lang/rust` pull request 166365 and `NixOS/nixpkgs` pull request 592370). hubdouble has no background job and counts reads instead: after a change that makes mergeability stale, the next `reads` reads answer `null` (2 by default, set by the [`mergeability`](seed.md#mergeability) kind), and the work runs right after the last of them. A read is the REST pull request read or a GraphQL read of `mergeable` or `mergeStateStatus`. `POST /_hubdouble/repos/{owner}/{repo}/pulls/{pull_number}/mergeability` ends the wait at once. |
| Test merge after a base push | A base push changes no pull request's `base.sha`, `merge_commit_sha`, `mergeable` or `rebaseable`, and REST and GraphQL reads do not change them either (35 open pull requests whose base had moved, each read twice with REST and GraphQL, in `cli/cli`, `sharkdp/bat`, `jqlang/jq`, `astral-sh/ruff`, `home-assistant/core` and `microsoft/vscode`, and `sharkdp/bat` pull request 4148 over two days). GitHub later computes new test merges on the new base and keeps `base.sha`, at a time it does not publish: 18 open `cli/cli` pull requests got a test merge on `7346a9cb` at 2026-11-23T12:56:44Z or a second later, and none on the five later tips, while `sharkdp/bat` pull requests got theirs at scattered times. The docs name a view of the pull request page as one cause. hubdouble has no web pages, so it keeps the snapshot until the next head push, base change or reopen, or until the admin route above computes it. |
| Merge state values | `mergeable_state` and GraphQL `mergeStateStatus` never give `has_hooks` or `draft`. The [GraphQL schema](https://docs.github.com/en/graphql/reference/enums#mergestatestatus) gives `HAS_HOOKS` for "passing commit status and pre-receive hooks", which only GitHub Enterprise Server runs, and hubdouble runs no pre-receive hooks. The schema marks `DRAFT` deprecated, and live GitHub answered another state for each of about 60 sampled drafts (`jqlang/jq` pull request 3750 `clean`, `cli/cli` pull request 14927 `blocked`). hubdouble answers a draft as a ready pull request. |
| Author association values | `author_association` and GraphQL `authorAssociation` never give `FIRST_TIMER`, `FIRST_TIME_CONTRIBUTOR` or `MANNEQUIN`. In about 900 sampled pull requests in nine repositories, among them `cli/cli`, `golang/go` and `firstcontributions/first-contributions`, live GitHub gave an author with only an open first pull request `NONE` (`cli/cli` pull request 15111), also in the `opened` webhook ([community discussion 78038](https://github.com/orgs/community/discussions/78038)). A mannequin is a placeholder for an unclaimed user that an import makes, and hubdouble has no imports. |
| Pull request state order | `Issue.closedByPullRequestsReferences` accepts `orderByState`. The argument has no effect. The [GitHub schema](https://docs.github.com/en/graphql/reference/issues#issue) gives no sort direction, and the client omits the argument. |
| Commit list date that cannot be read | When Ruby's `DateTime.parse` cannot read `since` or `until`, live GitHub answers `500` with an empty JSON body (`cli/cli`, `since=garbage`, 2026-11-24). The [docs](https://docs.github.com/en/rest/commits/commits#list-commits) give a `500` an error body with `message` and `documentation_url`. hubdouble answers `500` with that body. |
| Installation list `since` | The [installation list docs](https://docs.github.com/en/rest/apps/apps#list-installations-for-the-authenticated-app) describe `since` with the same text as the comment lists and publish no boundary. A live read needs an App's JWT. hubdouble reads `since` as the comment lists do: Ruby's `Time.parse` in Pacific time, a `422` with the comment lists' message for a time that it cannot read, and an installation updated at or after the time, with the microseconds kept. |
GitHub documents redirect responses for the [repository endpoint](https://docs.github.com/en/rest/repos/repos#get-a-repository) and more qualifiers for [issue and pull request search](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests).

## REST, IDs, and commits

- Errors use `message`, `documentation_url`, and a string `status`. A validation error can include `errors` entries with `resource`, `field`, and `code`.
- Page-based lists accept `page` and `per_page` (default 30, maximum 100). Responses include `Link` when there are other pages. A `Link` repeats each query name once, with its last value. Operations with cursors, such as App deliveries, use cursor pagination. An empty list is `[]`.
- A page list answers `422` when `page * per_page` is larger than `9223372036854775807`. The repository issue list without `after` or `before` answers `422` when `page * (per_page + 1)` is larger than 10 000, the repository comment list past 30 000 results, releases past 10 000 and workflow runs past 40 000.
- Successful API GET responses use a weak `ETag` derived from the media type and response body. A match with `If-None-Match` returns `304`.
- API responses include GitHub request, media type, version, and rate-limit headers. Rate-limit counters are fixed and the remaining count stays above zero unless a fault overrides it. User tokens can receive `X-OAuth-Scopes`.
- The API accepts `X-GitHub-Api-Version` values `2022-11-28` and `2026-03-10`. It defaults to `2022-11-28` and returns `400` for other versions.
- New object IDs use a server-wide signed 64-bit sequence. An explicit admin ID at or below that sequence returns `422`. Current GraphQL node IDs have a type prefix and an opaque payload. For a resolved legacy base64 ID, GraphQL returns a `DEPRECATION` warning in `extensions` with `next_global_id`.
- Timestamps use RFC 3339 in UTC with second precision. Reads of an unchanged Git ref return the same target.
- The App delivery log retains the last 50,000 attempts per App.
- Merge commits and commits from `createCommitOnBranch` use committer `GitHub <noreply@github.com>` and the local web-flow key. Installation-token Git data commits without an author, committer, or signature use the same key. They report `verification.verified: true` and reason `valid`. Client-signed Git data commits report `unknown_key`. Other unsigned commits report `unsigned`.

## GraphQL

- The validation exception in the plan allows fields with the same response name to differ in nullability on mutually exclusive concrete types. The `originalCommentEdit` inventory document uses this for `pullRequest` on `IssueComment` and `PullRequestReviewComment`.
- A null from a failed non-null field propagates to the nearest nullable parent. GraphQL errors give a `type`, and execution errors identify the field with a `path` and source `locations`.
- Connections require `first` or `last`, with a maximum of 100. An unimplemented field returns `HUBDOUBLE_NOT_IMPLEMENTED` on its path. A repository the caller cannot see returns null with `NOT_FOUND` for that alias.

## Test controls

Use [admin faults](admin-api.md#state-request-log-and-faults) to substitute a response, such as a secondary rate limit, `502`, or an `X-GitHub-SSO` header. The rule controls the match, status, body, headers, delay, and count.

Workflow dispatch creates a run and its jobs. The double simulates run state and can issue a run token. It does not execute workflow jobs. Use the Actions admin routes or the seed's `auto_complete` option to control run state. A job patch in the Actions admin route can append `annotations` to the job's check run, in the form that the Checks API takes them.
